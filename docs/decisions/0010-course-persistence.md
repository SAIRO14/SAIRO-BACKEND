# 0010. 코스를 서버에 영속화한다

- **상태:** 수용됨
- **날짜:** 2026-07-26
- **관련:** Q-03, [ADR 0008](./0008-greedy-nearest-neighbor-course-sort.md)

## 맥락

`POST /courses`가 `courseId`를 발급하면서도 결과를 어디에도 저장하지 않았다. `courses` 테이블도 없었다.
발급된 ID는 응답이 나가는 순간 의미를 잃었고, 서버는 그 ID가 무슨 코스였는지 알지 못했다.

이 때문에 두 곳이 막혀 있었다.

- **공유** — `POST /courses/{courseId}/share`가 경로의 `courseId`를 쓰지 못하고 요청 본문을 그대로 저장했다.
  서버가 만들지 않은 코스로도 공유 링크를 받을 수 있었고, 스냅샷에 지역이 없어 공유 상세에서 지역명을 표시할 수 없었다.
- **저장 여행지** — 저장 단위가 "추천 지역과 그 시점의 코스 스냅샷"인데 참조할 코스가 서버에 없어 API 설계를 시작할 수 없었다.

## 결정

`courses` 테이블을 만들고 `POST /courses`가 생성 결과를 저장한다.
`course_data` JSONB에 **지역명과 Day 1·Day 2를 함께** 담는다 (`course/CourseSnapshot`).

공유는 요청 본문을 받지 않는다. 경로의 `courseId`로 저장된 코스를 읽어 스냅샷을 복사한다.
없는 코스면 404 `COURSE_NOT_FOUND`다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 저장·공유 요청 본문에 스냅샷을 통째로 받는다 (Q-03의 A안) | 스키마 변경 없이 지금 구조 그대로 진행 가능 | 클라이언트가 보낸 내용을 검증 없이 신뢰한다. 공유 P0가 그대로 남고, 나중에 이 결정으로 옮길 때 저장·공유를 다시 손대야 한다 |
| 코스를 만들지 않고 추천 시점에 미리 저장 | 코스 생성 API가 없어도 됨 | 지역당 코스가 여러 개고 사용자가 고르기 전에 전부 저장하게 된다 |
| 공유가 `courses`를 외래키로 참조하고 스냅샷을 복사하지 않는다 | 중복 저장 없음 | 원본 코스가 바뀌거나 지워지면 과거 공유 링크의 내용이 함께 바뀐다. "공유 당시 데이터와 동일" 요구를 어긴다 |

## 결과

- 좋아지는 것: 서버가 만든 코스만 공유된다. 공유 스냅샷에 지역이 들어간다.
  저장 여행지가 참조할 대상이 생겼다. 한 코스의 공유 링크가 하나로 고정돼 공유 생성이 멱등해졌다.
- 나빠지거나 감수하는 것: 코스가 계속 쌓인다. 정리 정책이 없다.
  코스 스냅샷과 공유 스냅샷에 같은 내용이 두 벌 저장된다 (불변 스냅샷을 위해 감수한다).
  `POST /courses/{courseId}/share`가 요청 본문을 받지 않는 형태로 바뀌어 클라이언트 수정이 필요하다.
- 이 결정에 뒤따라야 하는 작업: 저장 여행지 API 설계 (중복 저장 판정 키는 [Q-04](../open-questions.md)),
  코스·공유 데이터 정리 정책 ([Q-02](../open-questions.md))

## 다시 검토해야 할 시점

- 코스 테이블이 정리 없이 커져 저장 비용이 문제가 될 때
- 공유가 아닌 다른 곳에서 코스를 수정할 필요가 생길 때 (지금은 생성 후 불변이 전제다)
