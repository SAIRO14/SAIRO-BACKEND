# 0013. ID 형식 검증은 값의 위치가 아니라 거짓 응답 가능성으로 정한다

- **상태:** 수용됨
- **날짜:** 2026-08-01
- **관련:** 이슈 #32, PR #55, [ADR 0001](./0001-error-response-contract.md), [ADR 0010](./0010-course-persistence.md)

## 맥락

[api-contract.md §2](../api-contract.md#2-상태-코드)에는 "리소스가 없는 것과 입력이 잘못된 것을
구분한다 — 형식이 맞는 ID인데 대상이 없으면 404, 형식 자체가 틀렸으면 400"이라는 규칙이 있었고,
여기 **예외**가 하나 붙어 있었다.

> 경로의 리소스 ID는 형식을 검증하지 않고 404로 답한다. `courseId`, `shareId`가 여기 해당한다.
> 형식 오류와 부재를 구분해주면 어떤 형식이 유효한지 알려주게 되어 ID를 탐색할 여지가 생긴다.

즉 **같은 성질의 식별자가 URL의 어디에 실렸는지에 따라** 정책이 갈렸다.
본문에 있으면 Bean Validation으로 400, 경로에 있으면 형식을 보지 않고 404였다.

저장 해제(#32)를 만들면서 이 경계가 임의적이라는 것이 드러났다.
`savedTripId`를 쿼리 파라미터로 받은 것은 보안 성질이 달라서가 아니라
[requirements.md §4](../requirements.md)의 **"식별자를 URL 경로에 두지 않는다"는 모양 제약** 때문이었다.
같은 값이 제약 하나 때문에 위치가 바뀌었고, 그 결과 정책까지 바뀌었다.

두 가지를 확인했다.

**예외의 근거가 성립하지 않는다.** 유효한 형식은 감춰져 있지 않다.
Swagger `@Parameter(example = ...)`에 그대로 적혀 있고, `POST /courses`는 발급한 `courseId`를
응답으로 돌려준다. 탐색해서 알아낼 것이 없다.

**검증하지 않아서 나가는 거짓 응답은 실재했다.** 서버가 발급하는 ID는 `UUID.randomUUID()`라
소문자 UUID v4인데, 이 값들이 담긴 컬럼은 `TEXT`라 조회가 대소문자를 구분한다.

```
POST /courses/8F14E45F-EA8D-4F4A-9C1B-2C3D4E5F6A7B/share
  → 404 COURSE_NOT_FOUND
```

코스는 실재하는데 "그런 코스가 없다"고 답한다. 대문자로 바꿔 쓴 클라이언트는
자기 코스가 사라졌다고 판단한다.

## 결정

**형식을 검증할지는 값이 어디 실려 왔는지가 아니라, 검증하지 않았을 때 무엇이 나가는지로 정한다.**

기준은 하나다 — 틀린 형식을 흘려보내면 **거짓 응답**이 나가는가.

- 나가면 400이다. 경로에 있어도 검증한다.
- 나갈 게 없으면(읽기 전용 조회) 검증하지 않고 404로 답한다.

"경로 ID는 형식을 검증하지 않는다"는 예외를 폐기한다.

이 결정에 따라 `POST /courses/{courseId}/share`가 형식 오류에 400을 낸다.
`GET /courses/shared/{shareId}`는 그대로 404다 — 없는 것을 없다고 답하는 것뿐이라 거짓이 아니다.
`shareId`는 10자리 소문자 hex로 형식도 다르다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 예외를 그대로 둔다 | 변경 없음 | 근거("형식 노출")가 사실이 아니고, 실재하는 코스에 404를 내보내는 비용이 남는다 |
| 예외를 아예 폐기하고 **모든** 경로 ID를 검증 | 규칙이 가장 단순 | `GET /courses/shared/{shareId}`까지 400으로 바뀌어 이미 배포된 공유 링크의 오류 응답이 달라진다. 얻는 것 없이 클라이언트 영향만 생긴다 |
| 위치 기준을 유지하되 저장 해제만 예외 처리 | 범위가 가장 작다 | 예외의 예외가 된다. 다음 사람이 어느 쪽을 따라야 할지 알 수 없다 |
| 컬럼을 `citext`로 바꿔 대소문자 문제를 없앤다 | 애플리케이션 규칙이 필요 없어진다 | 마이그레이션이 필요하고, 비-v4처럼 대소문자와 무관한 형식 오류는 그대로 남는다 |

## 결과

- 좋아지는 것:
  - 같은 성질의 식별자가 URL 위치 때문에 다르게 다뤄지지 않는다.
  - `POST /courses/{courseId}/share`가 실재하는 코스에 "없다"고 답하지 않는다.
  - 새 엔드포인트를 만들 때 물어볼 질문이 하나로 줄어든다 — "안 걸러도 응답이 정직한가."
- 나빠지거나 감수하는 것:
  - 형식 상수(`common/IdFormat`)를 검증이 필요한 자리마다 붙여야 한다. 빠뜨리면 예전 동작으로 돌아간다.
  - `POST /courses/{courseId}/share`의 오류 응답이 일부 입력에서 404 → 400으로 바뀐다.
    형식이 틀린 요청은 원래도 성공한 적이 없어 정상 흐름에는 영향이 없다.
- 이 결정에 뒤따라야 하는 작업:
  - 경로에 식별자를 두는 엔드포인트를 새로 만들 때 이 기준을 적용한다.
  - `shareId`에 형식 상수가 필요해지면 `IdFormat`에 함께 둔다. 지금은 필요하지 않다.

## 다시 검토해야 할 시점

- 식별자 컬럼을 `citext`나 `uuid` 타입으로 바꾸면 대소문자 논거가 사라지므로 다시 본다.
- 서버가 발급하는 ID 형식이 UUID v4가 아니게 되면 다시 본다.
