# 0015. 취향 분석 시 코스를 즉시 생성한다

- **상태:** 수용됨
- **날짜:** 2026-08-03
- **관련:** [ADR 0010](./0010-course-persistence.md), PR #67

## 맥락

[ADR 0010](./0010-course-persistence.md)은 코스 영속화 시점을 논의하면서
"분석 요청에 코스를 즉시 생성한다"와 "클라이언트가 지역을 선택한 뒤 별도 요청으로 생성한다"
두 가지를 검토하고, **분석 후 별도 요청**을 1차 결정으로 채택했다.

이후 구현을 진행하면서 다음 문제가 드러났다.

1. 분석 응답에 `analysisId`가 실렸고, 클라이언트는 이를 `/recommendations?analysisId=`로
   재요청해야 했다. 그 자체로 불필요한 왕복이었다.
2. 분석 결과를 담은 `AnalysisStore`가 TTL 없는 `ConcurrentHashMap`이어서 메모리가 계속
   쌓였다. 서버를 재시작하면 분석 결과가 사라지고, 인스턴스가 여럿이면 결과가 흩어진다.
   적절한 해법 없이 임시로 두기 어렵다.
3. 코스 생성 요청(`POST /courses`) 흐름을 따로 유지해야 해서 경로가 두 갈래로 남았다.

## 결정

`POST /taste-analysis`가 내부에서 코스를 즉시 생성·저장하고 `courseId`를 응답에 담는다.
단일 요청으로 분석과 코스 생성이 완료되며, 클라이언트는 추가 요청 없이 저장·공유에 바로 진입할 수 있다.

ADR 0010의 "분석 후 별도 요청" 방식은 이 결정으로 대체된다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 분석 후 별도 요청 (ADR 0010 1차 결정) | 재시도해도 코스가 늘지 않음 | 클라이언트 왕복 최소 2회. AnalysisStore TTL 문제를 그대로 안고 감 |
| AnalysisStore를 Redis나 DB로 교체 | 다중 인스턴스·재시작에 강해짐 | 별도 저장소 추가 없이 즉시 생성으로 문제 자체를 없앨 수 있음 |

## 결과

- 좋아지는 것: 클라이언트 왕복이 1회로 준다. AnalysisStore와 `GET /recommendations`가 불필요해진다.
- 나빠지거나 감수하는 것: 같은 분석을 재시도하면 코스가 최대 3개씩 추가로 쌓인다.
  중복 제거 로직은 두지 않는다. 코스 볼륨이 문제가 될 만큼 커지면 그때 정리 배치를 검토한다.
  (ADR 0014와 같은 감수 결정)
- 이 결정에 뒤따라야 하는 작업: `AnalysisStore`와 `GET /recommendations` 제거 (후속 이슈)

## 다시 검토해야 할 시점
