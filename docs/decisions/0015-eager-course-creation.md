# ADR 0015 — 취향 분석 시 코스 즉시 생성

날짜: 2026-08-03
상태: 확정

## 배경

[ADR 0010](./0010-course-persistence.md)은 코스 영속화 시점을 논의하면서
"분석 요청에 코스를 즉시 생성한다"와 "클라이언트가 지역을 선택한 뒤 별도 요청으로 생성한다"
두 가지를 검토하고, **분석 후 별도 요청**을 1차 결정으로 채택했다.

이후 구현을 진행하면서 다음 문제가 드러났다.

1. 분석 응답에 `analysisId`가 실렸고, 클라이언트는 이를 `/recommendations?analysisId=`로 재요청해야 했다. 그 자체로 불필요한 왕복이었다.
2. 분석 스토어(`AnalysisStore`)의 TTL(인메모리 15분)이 너무 짧거나 너무 길다는 판단이 계속 나왔다. 적정 TTL 없이 임시로 두기 어렵다.
3. 코스 생성 요청(`POST /courses`) 흐름을 따로 유지해야 해서 경로가 두 갈래로 남았다.

## 결정

`POST /taste-analysis`가 내부에서 코스를 즉시 생성·저장하고 `courseId`를 응답에 담는다.
단일 요청으로 분석과 코스 생성이 완료되며, 클라이언트는 추가 요청 없이 저장·공유에 바로 진입할 수 있다.

ADR 0010의 "분석 후 별도 요청" 방식은 이 결정으로 대체된다.

## 구현 세부

- `TasteAnalysisService.analyzeAndBuildCourses()`에 `@Transactional`을 붙여 최대 3번의 `courseRepository.save()` 호출을 한 트랜잭션으로 묶는다.
- `AnalysisStore`와 `GET /recommendations`는 deprecated 상태로 남기고 이후 제거한다. (#61)
- 같은 분석을 재시도하면 코스가 최대 3개씩 추가로 쌓인다. 중복 제거 로직은 두지 않는다. 코스 볼륨이 문제가 될 만큼 커지면 그때 정리 배치를 검토한다. (ADR 0014와 같은 감수 결정)

## 트레이드오프

| | 즉시 생성(채택) | 별도 요청(ADR 0010) |
|---|---|---|
| 클라이언트 왕복 | 1회 | 최소 2회 |
| 분석 스토어 TTL | 불필요 | 필요 |
| 재시도 시 코스 중복 | 최대 3개씩 누적 | 없음 |
| 코스 테이블 볼륨 | 더 빠르게 증가 | 느리게 증가 |

재시도로 인한 코스 누적은 감수한다. 정리 배치 없이 볼륨이 쌓이는 것도 ADR 0014와 같은 이유로 감수한다.
