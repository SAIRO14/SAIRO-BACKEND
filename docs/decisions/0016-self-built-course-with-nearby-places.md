# 0016. 코스는 자체 스팟으로 만들고 주변 장소는 TourAPI로 실시간 조회한다

- **상태:** 수용됨
- **날짜:** 2026-08-05
- **관련:** 이슈 #51, 2026-08-03 2차 회의, [ADR 0008](./0008-greedy-nearest-neighbor-course-sort.md), [ADR 0009](./0009-tourapi-curated-course-source.md)(대체), [ADR 0015](./0015-eager-course-creation.md)

## 맥락

코스를 무엇으로 만들 것인가가 두 갈래로 갈려 있었다.

[ADR 0009](./0009-tourapi-curated-course-source.md)는 TourAPI `contentTypeId=25`(여행 코스)를
그대로 가져다 쓰기로 했다. 하지만 그 구현은 어디에도 들어가지 않았다.
유일한 구현이던 PR #16이 2026-07-27에 머지 없이 닫혔고,
`TourApiClient`에는 장소 상세를 가져오는 `fetchDetail` 하나만 남았다.
실제 코스는 자체 `spots` 테이블에서 greedy nearest-neighbor로 만들어지고 있었다([ADR 0008](./0008-greedy-nearest-neighbor-course-sort.md)).
**문서와 코드가 3개월 가까이 어긋난 채였다.**

동시에 "추천 결과에 무엇을 담을 것인가"가 제품 쪽에서 열려 있었다.

| 안 | 내용 |
|---|---|
| C안 | 관광지만 보여준다 (현재 구현, 클라이언트 UI도 이 기준) |
| B안 | 관광 코스에 더해 주변 식당·숙박·카페를 함께 보여준다 |

2026-08-03 2차 회의에서 C안은 코스 추천 경험을 살리기 어렵다는 데 공감했고,
**주변 장소는 이미지까지 제공할 수 있어야 의미가 있다**는 것을 B안의 선결 조건으로 걸었다.

2026-08-04 API 조사 결과는 이랬다.

| API | 이미지 | 무료 한도 | 판단 |
|---|---|---|---|
| 카카오 로컬 | 없음 | 10만 건/일 | 이미지가 없어 B안 불가 |
| 네이버 지역 검색 | 없음 | 25,000건/일 | 이미지가 없어 B안 불가 |
| Google Places (New) | 있음 | 월 $200 크레딧(약 1,000건) | 이미지 포함 시 Pro~Enterprise 티어. 비용 부담 |
| TourAPI | 있음 (공식) | 하루 10,000건(추정) | 무료지만 식당·숙박 누락이 많음 |

즉 **무료로 이미지를 얻을 수 있는 곳은 TourAPI뿐인데, 그 데이터는 절대량이 부족했다.**

## 결정

**코스 본체는 자체 `spots` 테이블에서 만들고, 주변 식당·숙박·카페는 TourAPI로 실시간 조회해 덧붙인다.**

- 코스 생성은 지금처럼 자체 스팟 + greedy nearest-neighbor를 유지한다 ([ADR 0008](./0008-greedy-nearest-neighbor-course-sort.md)).
- TourAPI는 **코스의 원천이 아니라 주변 장소의 원천**으로만 쓴다. `contentTypeId`로 식당·숙박을 구분한다.
- 데이터 절대량이 부족한 것은 감수한다. 관광데이터 활용 공모전이라는 성격상
  **양이 적더라도 관광 데이터를 쓰는 쪽**을 택했고, 추후 확장하기로 했다.
- 이미지가 없는 장소는 Google Places로 보완하거나 노출에서 제외한다.
  **둘 중 어디까지 보완할지는 아직 정하지 않았다** → [Q-10](../open-questions.md)

### 언제 부르는가

**코스를 조회하는 시점에 부른다. `POST /taste-analysis` 응답에는 넣지 않는다.**

[ADR 0015](./0015-eager-course-creation.md)로 코스 생성이 분석 요청 안으로 들어왔기 때문에
"코스 확정 시"라는 말이 두 가지로 읽힌다. 호출량이 이만큼 다르다.

| 시점 | 분석 1회당 TourAPI 호출 |
|---|---|
| 분석 시점 (`POST /taste-analysis`) | 코스 3개 × 관광지 최대 5개 = **최대 15회** + 이미지 보완 |
| **코스 조회 시점 (채택)** | 사용자가 실제로 연 코스 1개분 = **최대 5회** + 이미지 보완 |

분석 시점을 버린 이유는 셋이다.

1. **응답 시간.** 사용자가 사진을 고르고 기다리는 그 요청 안에 외부 호출 15회가 붙는다.
2. **쿼터.** TourAPI 하루 10,000건(추정) 기준으로 분석 1회 = 15건이면 하루 660분석이 상한이다.
   공모전 시연·심사 기간에 닿을 수 있는 수치다.
3. **재시도 낭비.** ADR 0015는 "같은 분석을 재시도하면 코스가 최대 3개씩 쌓인다"를 감수했다.
   분석 시점에 주변 장소를 부르면 **감수 대상이 DB 행에서 외부 쿼터로 바뀐다.**
   ADR 0015가 그 값을 매길 때는 외부 호출이 붙어 있지 않았다.

**따라오는 것: 주변 장소는 코스 스냅샷에 넣지 않는다.**
저장·공유는 지금처럼 지역과 코스만 스냅샷으로 굳히고, 주변 장소는 열 때마다 새로 붙는다.
따라서 **공유 링크가 재현하는 "공유 당시 상태"에 주변 장소는 포함되지 않는다.**
식당·숙박은 폐업·운영시간 변경이 잦아 굳혀두면 오히려 틀린 정보가 되므로 이쪽이 맞다고 봤다.

### 어디서 찾는가

**각 관광지를 기준으로 약 3km 반경에서 찾고, 결과를 합칠 때 중복을 제거한다.**

TourAPI의 주변 조회는 점 + 반경(`mapX`/`mapY`/`radius`)이라 영역 조회를 직접 주지 않는다.
어떤 모양을 잡든 결국 관광지별 반경 조회 여러 번으로 쪼개진다.
코스 하나에 관광지가 최대 5개이고 3km 반경이 서로 겹치므로 **같은 식당이 여러 번 나온다.**
중복 제거는 선택이 아니라 필수다.

> 관광지 간 거리가 가까울 때 이동 경로를 감싸는 영역으로 한 번에 훑는 방식은
> **최적화 아이디어로 남겨둔다.** 호출 횟수는 어차피 관광지 수만큼이라 이득이 크지 않고,
> "감싸는 영역"의 모양(bounding box인지 회랑인지, 회랑이면 폭이 얼마인지)이 정해지지 않았다.

**반경 판정은 TourAPI에 맡긴다.** 3km는 `radius` 파라미터(미터)로 넘기고 우리가 거리를 계산하지 않는다.

> **코스 정렬의 거리 기준을 여기에 가져다 쓰면 안 된다.**
> `CourseService`가 쓰는 값은 위경도 차의 **제곱합(유클리드)** 이고
> [recommendation.md](../recommendation.md)가 적어둔 대로 실제 지구 거리가 아니다.
> **순서를 정하는 용도라 단조 관계만 유지되면 충분해서** 제곱근도 생략한다.
> 절대 거리인 "3km"를 그 값으로 판정할 수 없다.
> 우리 쪽에서 거리 계산이 필요해지면(예: 중복 제거 시 근접 장소 병합)
> 그때는 **haversine 같은 실제 거리 함수를 새로 들여야 한다.** 기존 함수를 재사용하지 않는다.

이 결정으로 [ADR 0009](./0009-tourapi-curated-course-source.md)를 **대체**한다.
TourAPI는 계속 쓰지만 용도가 바뀌었다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| C안 유지 (관광지만) | 추가 구현 없음, 외부 호출 안 늘어남, 클라이언트 UI 그대로 | 코스 추천인데 먹고 잘 곳이 없다. 회의에서 "코스 추천 경험을 살리기 어렵다"는 데 공감 |
| ADR 0009 유지 (TourAPI 큐레이션 코스를 코스 원천으로) | 관광공사가 편집한 검증된 코스 | 3개월간 구현되지 않았고 PR #16이 닫혔다. 사진 임베딩 기반 추천과 결이 맞지 않는다 — 우리 추천은 사진에서 나온 지역인데 코스는 남이 짠 것이 된다 |
| 카카오 로컬 / 네이버 지역 검색 | 무료 한도 넉넉, 한국 데이터 품질 좋음, 식당·숙박 풍부 | **이미지를 제공하지 않는다.** 이미지 없는 주변 장소는 B안을 채택한 이유 자체를 없앤다 |
| Google Places를 주 소스로 | 이미지·평점·운영시간까지 한 번에 | 무료 한도가 월 1,000건 수준. 이미지 포함 시 Pro~Enterprise 티어라 MVP 예산 밖 |
| 주변 장소를 자체 DB에 미리 적재 | 응답 빠름, 외부 장애 무관 | 수집·유지보수 비용. 8/14 MVP 목표 안에 들어가지 않는다 |

## 결과

- 좋아지는 것
  - 문서와 코드의 3개월짜리 불일치가 사라진다. ADR 0009가 기술하던 미구현 기능이 정리됐다.
  - 코스는 우리 추천 로직이 만들고, 주변 정보만 외부에서 채운다. 책임 경계가 분명하다.
  - 관광 데이터를 실제로 쓰므로 공모전 취지에 맞는다.
- 나빠지거나 감수하는 것
  - **TourAPI의 식당·숙박 절대량이 부족하다.** 지역에 따라 주변 장소가 거의 없거나 아예 없는 코스가 나온다.
  - **외부 호출이 2단이 된다.** 코스 조회 1회당 TourAPI 최대 5회(관광지 수만큼)를 부르고,
    이미지가 없는 장소마다 Google Places를 한 번 더 거친다. 이미지 결측률에 따라 총 호출은 그 배가 된다.
  - **공유 링크가 주변 장소까지 재현하지는 않는다.** 스냅샷 대상이 아니므로 열 때마다 달라질 수 있다.
  - 이미지 없는 장소를 걸러내면 실제 노출량은 조회량보다 더 줄어든다.
  - 클라이언트 UI가 C안 기준으로 구현돼 있어 결과·지도 화면 보완이 필요하다.
- 이 결정에 뒤따라야 하는 작업
  - **[Q-09](../open-questions.md) 요청 타임아웃을 먼저 닫아야 한다.** 외부 호출이 늘어난 만큼
    무한 대기 경로를 만들지 않는 것이 이 기능의 선결 조건이다.
    **타임아웃 값만으로는 부족하다** — 관광지 5개를 순차로 부르면 상한이 5배가 되므로
    병렬 호출 여부와 코스당 조회 상한을 함께 정해야 한다.
    → **2026-08-07에 닫혔다. [ADR 0017](./0017-request-timeouts.md).**
  - 주변 장소가 0건인 코스의 응답 형태를 정한다.
  - 유형 매핑을 정한다. **카페는 `contentTypeId`로 나뉘지 않는다** → [Q-11](../open-questions.md)
  - 이미지 결측 처리 기준을 정한다 ([Q-10](../open-questions.md)).
  - `PRD §4.2`에서 "코스 스팟 주변 카페·식당 자동 보완"을 Out of Scope에서 뺀다. (이 ADR과 함께 반영)

## 다시 검토해야 할 시점

- TourAPI 주변 장소 커버리지가 실사용에서 견딜 수 없을 만큼 낮을 때 → 카카오 로컬(정보) + TourAPI/Google(이미지) 조합 재검토
- Google Places 보완 비용이 무료 한도를 넘길 때
- 주변 장소 조회가 응답 시간 상한을 반복해서 넘길 때 → 사전 적재 또는 캐싱으로 이전
