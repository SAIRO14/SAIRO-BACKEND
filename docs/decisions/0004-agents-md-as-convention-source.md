# 0004. AGENTS.md를 코딩 규약 정본으로

- **상태:** 수용됨
- **날짜:** 2026-07-23
- **관련:** 이슈 #18, PR #19

## 맥락

패키지 구조, 계층 규칙, DTO 배치 기준이 어디에도 적혀 있지 않았다.
새로 합류한 사람이나 AI 에이전트가 코드를 쓰려면 기존 코드를 읽어 추측해야 했다.

추측이 어려운 함정도 몇 개 있었다.

- Spring Boot 4는 Jackson 3을 쓴다. 패키지가 `tools.jackson`이라
  습관대로 `com.fasterxml.jackson`을 임포트하면 컴파일이 깨진다.
- JPA와 `JdbcTemplate`을 함께 쓰는데 어느 쪽을 언제 쓰는지 기준이 없었다.
- `ddl-auto: validate`라 엔티티와 스키마가 어긋나면 애플리케이션이 아예 뜨지 않는다.

AI 에이전트용 문서 형식도 정해야 했다. `CLAUDE.md`, `AGENTS.md` 등 도구마다 관례가 다르고,
같은 내용을 여러 파일에 두면 서로 어긋난다.

## 결정

**`AGENTS.md`를 코딩 규약의 유일한 정본으로 둔다.**
`CLAUDE.md`는 규약을 복제하지 않고 AGENTS.md를 참조하는 얇은 진입점으로만 유지한다.

역할을 이렇게 나눈다.

| 문서 | 담당 |
|---|---|
| `AGENTS.md` | 코드를 **어떻게** 쓰는가 — 구조, 계층, 오류 처리, 테스트 |
| `docs/` | **무엇을 왜** 만드는가 — 요구사항, 결정, 미결 항목 |
| `CONTRIBUTING.md` | 브랜치·커밋·PR 절차 |
| `README.md` | 프로젝트 소개와 로컬 실행 |

AGENTS.md에는 **코드베이스에 실제로 존재하는 패턴만** 적는다. 앞으로의 계획은 넣지 않는다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| CLAUDE.md 하나만 둔다 | 파일이 하나로 끝난다 | 특정 도구 이름에 묶인다. 다른 에이전트나 사람이 볼 문서로는 이름이 맞지 않는다 |
| 두 파일에 같은 내용을 복제 | 어느 쪽을 열어도 바로 읽힌다 | 한쪽만 고치는 일이 반드시 생긴다. 어긋난 규약은 없는 규약보다 나쁘다 |
| 규약을 `docs/`에 넣는다 | 문서가 한곳에 모인다 | 규약은 코드를 쓸 때마다 보고 요구사항은 작업을 시작할 때 본다. 참조 빈도와 대상이 달라 섞으면 둘 다 찾기 어려워진다 |
| CONTRIBUTING.md에 합친다 | 새 파일이 없다 | 절차 문서와 코딩 규약은 성격이 다르다. 이미 있는 CONTRIBUTING의 초점이 흐려진다 |

## 결과

**좋아지는 것**

- 규약을 고칠 때 한 파일만 보면 된다.
- 도구 이름에 묶이지 않아 사람도 같은 문서를 본다.
- "무엇을 만드나"와 "어떻게 만드나"가 분리돼 필요한 문서를 빨리 찾는다.

**감수하는 것**

- `CLAUDE.md`만 읽는 도구는 한 단계를 더 따라가야 한다.
  이를 줄이려고 자주 놓치는 함정 몇 개는 CLAUDE.md에도 짧게 남겼다.
  **규약 자체는 복제하지 않는다.**
- 코드가 바뀌면 AGENTS.md도 함께 낡는다. "실제 존재하는 패턴만 적는다"는 원칙이
  이를 줄이지만 없애지는 못한다.

**뒤따라야 하는 작업**

- 규약이 바뀌면 AGENTS.md만 고친다. CLAUDE.md에 규약을 추가하지 않는다.

## 다시 검토해야 할 시점

에이전트 도구 생태계에서 다른 파일명이 사실상 표준이 되면 진입점 파일을 다시 본다.
정본이 AGENTS.md라는 구조 자체는 그대로 둔다.
