# 0011. 저장 여행지의 중복 판정은 장소 구성으로 한다

- **상태:** 수용됨
- **날짜:** 2026-07-30
- **관련:** Q-04, [ADR 0010](./0010-course-persistence.md), [ADR 0008](./0008-greedy-nearest-neighbor-course-sort.md)

## 맥락

저장 여행지는 "같은 추천 결과는 중복 저장 불가, 같은 지역이라도 코스가 다르면 별도 저장"이 요구사항이다.
무엇을 "같은 것"으로 볼지 정하지 않으면 유니크 제약을 쓸 수 없어 저장 API 전체가 막혀 있었다.

`courses` 테이블이 생겨 코스를 `course_id`로 참조할 수 있게 됐지만([ADR 0010](./0010-course-persistence.md)),
같은 장소로 `POST /courses`를 다시 부르면 매번 새 `course_id`가 나온다.
사용자가 추천 화면을 다시 거치기만 해도 새 ID가 생기므로 `course_id`로는 중복을 판정할 수 없다.

## 결정

저장 항목의 정체성을 **`(익명 사용자 ID, 코스 지문)`** 으로 정한다.
`saved_trips`에 이 두 컬럼의 유니크 인덱스를 건다.

- **코스 지문** — Day 1·Day 2의 장소 ID를 **정렬해** 이어 붙인 값의 SHA-256이다 (`saved/CourseFingerprint`).
  **순서는 넣지 않는다.** 순서는 사용자가 고른 것이 아니라 좌표 정렬이 정하는 값이므로
  ([ADR 0008](./0008-greedy-nearest-neighbor-course-sort.md)), 정렬 방식을 바꾸면 과거 저장분과 지문이 어긋나
  같은 코스가 중복으로 쌓인다. 사용자가 고른 것은 "어느 장소들인가"다.

  **스냅샷 전체의 해시가 아니다.** 장소의 이름·좌표·이미지는 코스를 만든 시점의 `spots` 값이 복사된 것이라
  마스터가 바뀌면 달라진다. 그 차이까지 지문에 넣으면 장소 정보가 한 번 수정될 때마다
  사용자의 저장 목록에 같은 코스가 또 쌓인다.

- **코스 내용** — 저장 행은 `course_id`를 외래키로만 들고 스냅샷을 복사하지 않는다.

**따라서 정체성 키가 같다고 스냅샷 JSON이 같지는 않다.** 키가 같은 요청은 차이를 무시하고
최초 저장 시점의 `course_id`와 스냅샷을 그대로 유지한다.

### 지역명을 정체성에 넣지 않는 이유

`region_key` 컬럼은 남긴다. 응답의 `regionName`과 저장 목록의 지역 필터에 필요하다.
**다만 중복 판정에는 쓰지 않는다.**

`CourseService.resolveRegionName`이 한 코스의 모든 장소가 같은 `region_name`을 갖도록 강제한다.
따라서 장소 집합이 정해지면 지역명도 함께 정해진다 — 지문이 같으면 지역명도 같다.
**이 축은 서로 다른 코스를 갈라주는 일을 하지 못한다.**

같은 지문에 다른 지역명이 나오는 경로는 하나뿐이다. 두 코스 생성 사이에 `spots.region_name`
마스터가 수정된 경우다. 그때 지역명이 키에 있으면 같은 코스가 중복으로 쌓인다.
즉 넣어서 얻는 것은 없고 잃는 것만 있다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| `course_id`만으로 판정 | 가장 단순하다 | 같은 장소로 코스를 다시 만들면 새 ID가 나와 중복이 그대로 쌓인다 |
| 지문에 장소 순서를 포함 | 순서가 다른 코스를 다른 저장으로 구분할 수 있다 | 순서는 사용자 선택이 아니라 정렬 알고리즘의 결과다. 알고리즘을 바꾸는 순간 과거 저장분과 어긋난다 |
| 지역명을 정체성에 포함 (`(device_id, region_key, fingerprint)`) | 지역을 저장 단위의 일부로 명시적으로 표현한다 | 한 코스의 장소가 모두 같은 지역이어야 하므로 지문이 지역명을 이미 결정한다. 코스를 갈라주지 못하고, `spots.region_name`을 수정하면 같은 코스를 중복으로 쌓는 일만 한다 |
| 정규화된 지역 코드 도입 | `"경북"`/`"경상북도"` 같은 표기 흔들림에 강하다 | `spots` 데이터 정비와 매핑 테이블이 선행돼야 한다. 지역명이 정체성에서 빠졌으므로 저장 중복 문제로는 필요하지 않다 |
| 저장 행에 스냅샷 JSONB 복사 (`shared_courses` 방식) | `courses`가 지워져도 저장 목록이 살아남는다 | 같은 JSON이 두 벌 존재하고 한쪽만 고쳐질 여지가 생긴다. 공유와 달리 저장은 "당시 모습 그대로 재현"이 요구사항이 아니다 |

## 결과

- 좋아지는 것: 저장 생성이 멱등해졌다. 추천 화면을 다시 거쳐 새 `courseId`로 저장해도 항목이 하나다.
  지역이 같아도 장소 구성이 다르면 별도 저장이 된다. 저장 API(#30~#33)의 스키마가 풀렸다.
- 나빠지거나 감수하는 것:
  - **`SAVED_TRIP_CONFLICT` 409가 이 설계에서는 발생하지 않는다.**
    정체성 키가 같으면 스냅샷의 순서·표시 정보 차이는 중복 판정에서 무시하고 최초 저장 스냅샷을 유지하기 때문이다.
    충돌로 볼 상황 자체가 정의되지 않는다. 코드는 `ErrorCode`에 남겨두되 저장 생성 엔드포인트에 문서화하지 않는다.
  - 장소 구성이 같고 순서만 다른 코스를 사용자가 구분해 저장할 수 없다.
  - 저장 후 `spots.region_name`이 바뀌어도 저장 항목의 `region_key`는 최초 값 그대로다.
    목록에 옛 지역명이 남는다. 중복이 생기는 것보다는 낫다고 본다.
  - `courses`를 지우면 저장 행의 외래키가 막는다. 코스 정리 정책(당시 Q-02 —
    [ADR 0014](./0014-share-link-lifetime.md)로 확정됐다)에서 저장된 코스를 어떻게 다룰지
    함께 정해야 한다.
- 이 결정에 뒤따라야 하는 작업: 저장 목록 커서 페이지(#31), 저장 해제(#32), 저장 상태 반영(#33)

## 다시 검토해야 할 시점

- 코스 순서를 사용자가 직접 편집할 수 있게 될 때 (지문에서 순서를 뺀 전제가 깨진다)
- **여러 지역에 걸친 코스를 허용할 때.** 지금은 `resolveRegionName`이 단일 지역을 강제하므로
  지문이 지역명을 결정한다. 이 전제가 깨지면 같은 장소 집합이 두 지역으로 갈릴 수 있고,
  그때는 지역명을 정체성에 다시 넣어야 한다.
