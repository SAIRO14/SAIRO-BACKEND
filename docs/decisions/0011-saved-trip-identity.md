# 0011. 저장 여행지의 중복 판정은 지역과 장소 구성으로 한다

- **상태:** 수용됨
- **날짜:** 2026-07-30
- **관련:** Q-04, [ADR 0010](./0010-course-persistence.md), [ADR 0008](./0008-greedy-nearest-neighbor-course-sort.md)

## 맥락

저장 여행지는 "같은 추천 결과는 중복 저장 불가, 같은 지역이라도 코스가 다르면 별도 저장"이 요구사항이다.
무엇을 "같은 것"으로 볼지 정하지 않으면 유니크 제약을 쓸 수 없어 저장 API 전체가 막혀 있었다.

`courses` 테이블이 생겨 코스를 `course_id`로 참조할 수 있게 됐지만([ADR 0010](./0010-course-persistence.md)),
같은 장소로 `POST /courses`를 다시 부르면 매번 새 `course_id`가 나온다.
사용자가 추천 화면을 다시 거치기만 해도 새 ID가 생기므로 `course_id`로는 중복을 판정할 수 없다.

## 결정

저장 항목의 정체성을 **`(익명 사용자 ID, 지역명, 코스 지문)`** 으로 정한다.
`saved_trips`에 이 세 컬럼의 유니크 인덱스를 건다.

- **지역명** — `CourseSnapshot.regionName`을 그대로 쓴다.
  이 값은 요청 문자열이 아니라 서버가 `spots.region_name`에서 유도한 정규값이다([ADR 0010](./0010-course-persistence.md)).
  `"주"` 같은 부분 일치용 요청 값이 키에 들어올 수 없으므로 별도의 지역 코드 체계를 만들지 않는다.
- **코스 지문** — Day 1·Day 2의 장소 ID를 **정렬해** 이어 붙인 값의 SHA-256이다 (`saved/CourseFingerprint`).
  **순서는 넣지 않는다.** 순서는 사용자가 고른 것이 아니라 좌표 정렬이 정하는 값이므로
  ([ADR 0008](./0008-greedy-nearest-neighbor-course-sort.md)), 정렬 방식을 바꾸면 과거 저장분과 지문이 어긋나
  같은 코스가 중복으로 쌓인다. 사용자가 고른 것은 "어느 장소들인가"다.
- **코스 내용** — 저장 행은 `course_id`를 외래키로만 들고 스냅샷을 복사하지 않는다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| `course_id`만으로 판정 | 가장 단순하다 | 같은 장소로 코스를 다시 만들면 새 ID가 나와 중복이 그대로 쌓인다 |
| 지문에 장소 순서를 포함 | 순서가 다른 코스를 다른 저장으로 구분할 수 있다 | 순서는 사용자 선택이 아니라 정렬 알고리즘의 결과다. 알고리즘을 바꾸는 순간 과거 저장분과 어긋난다 |
| 정규화된 지역 코드 도입 | `"제주"`/`"제주도"` 같은 표기 흔들림에 강하다 | `spots` 데이터 정비와 매핑 테이블이 선행돼야 한다. 저장 키는 이미 정규값을 받으므로 지금 필요한 문제가 아니다 |
| 저장 행에 스냅샷 JSONB 복사 (`shared_courses` 방식) | `courses`가 지워져도 저장 목록이 살아남는다 | 같은 JSON이 두 벌 존재하고 한쪽만 고쳐질 여지가 생긴다. 공유와 달리 저장은 "당시 모습 그대로 재현"이 요구사항이 아니다 |

## 결과

- 좋아지는 것: 저장 생성이 멱등해졌다. 추천 화면을 다시 거쳐 새 `courseId`로 저장해도 항목이 하나다.
  지역이 같아도 장소 구성이 다르면 별도 저장이 된다. 저장 API(#30~#33)의 스키마가 풀렸다.
- 나빠지거나 감수하는 것:
  - **`SAVED_TRIP_CONFLICT` 409가 이 설계에서는 발생하지 않는다.** 키가 같으면 내용도 같기 때문이다.
    코드는 `ErrorCode`에 남겨두되 저장 생성 엔드포인트에 문서화하지 않는다.
  - 장소 구성이 같고 순서만 다른 코스를 사용자가 구분해 저장할 수 없다.
  - `courses`를 지우면 저장 행의 외래키가 막는다. 코스 정리 정책([Q-02](../open-questions.md))에서
    저장된 코스를 어떻게 다룰지 함께 정해야 한다.
- 이 결정에 뒤따라야 하는 작업: 저장 목록 커서 페이지(#31), 저장 해제(#32), 저장 상태 반영(#33)

## 다시 검토해야 할 시점

- 코스 순서를 사용자가 직접 편집할 수 있게 될 때 (지문에서 순서를 뺀 전제가 깨진다)
- `spots.region_name`의 표기 흔들림 때문에 같은 지역이 다른 키로 갈리는 사례가 나올 때
