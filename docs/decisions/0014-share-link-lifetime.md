# 0014. 공유 링크와 코스를 MVP에서 만료시키지 않는다

- **상태:** 수용됨
- **날짜:** 2026-08-01
- **관련:** 이슈 #34 (Q-02), [ADR 0010](./0010-course-persistence.md), [ADR 0011](./0011-saved-trip-identity.md), [ADR 0012](./0012-course-ownership.md), [PRD §12 #3](../PRD.md)

## 맥락

공유 코스를 얼마나 보관할지가 Q-02로 열려 있었다. 그런데 **PRD §12 #3은 이미
"MVP는 무기한, 볼륨 증가 시 30일 기준 재검토"로 확정돼 있었다.** 실제로 열려 있던 것은
만료 기간이 아니라 그 결정을 따랐을 때 뒤따르는 것들이었다.

현재 상태는 이렇다.

- `shared_courses`에 **만료 컬럼이 없다.** 정리 배치도 없다.
- `courses`도 지우는 경로가 없어 함께 쌓인다. ([ADR 0010](./0010-course-persistence.md)으로
  코스를 영속화하면서 생긴 결과다.)
- `saved_trips.course_id`는 `ON DELETE` 절 없이 `courses`를 참조한다.
  PostgreSQL에서 이 경우 기본 동작은 **`NO ACTION`**이고, 제약이 `NOT DEFERRABLE`이라
  삭제를 즉시 거절한다. **저장된 코스는 지우려 해도 외래키가 막는다.**
- `shared_courses.course_id`는 `ON DELETE SET NULL`이다. 스냅샷을 복사해 두므로
  코스가 사라져도 공유 링크는 계속 열린다.

`requirements.md` §6은 이것을 P2 격차("코스 정리")로 적어 두고 Q-02를 가리키고 있었다.

만료와 부재를 응답에서 구분하지 않는 것은 이미 정해져 있다.
([api-contract.md §2](../api-contract.md#2-상태-코드))

## 결정

**MVP에서 공유 링크와 코스는 만료하지 않는다. 정리 배치를 두지 않는다.**

PRD의 결정을 그대로 따르고, 그에 따라오는 것들을 아래와 같이 확정한다.

1. **스키마를 바꾸지 않는다.** `shared_courses`에 만료 컬럼을 넣지 않는다.
   만료가 없는데 컬럼을 두면 항상 NULL이거나 항상 미래인 값이 남고, 실제 정책이 정해질 때
   그 값의 의미를 다시 정의해야 한다.

2. **`saved_trips.course_id`가 코스 삭제를 막는 현재 동작을 유지한다. 방치가 아니라 의도다.**
   `saved_trips`는 스냅샷을 복사하지 않고 `courses`에서 내용을 가져오므로
   ([data-model.md](../data-model.md)), 코스가 사라지면 저장 항목이 내용을 잃는다.
   **삭제를 막는 쪽이 내용 없는 저장 항목을 남기는 쪽보다 낫다.**
   `ON DELETE`를 명시하는 마이그레이션도 추가하지 않는다. 동작이 이미 원하는 대로이고,
   삭제 경로가 없는 지금 스키마를 건드릴 근거가 없다.

   **나중에 이걸 명시하려거든 `ON DELETE RESTRICT`로 바꾸지 않는다.** 현재는 `NO ACTION`이고
   둘은 같지 않다 — `NO ACTION`은 제약이 `DEFERRABLE`이면 커밋 시점까지 검사를 미룰 수 있지만
   `RESTRICT`는 그럴 수 없다. 지금은 `NOT DEFERRABLE`이라 결과가 같을 뿐이다.

3. **무한 증가를 감수한다.** 출시 전이고 트래픽이 없다. 정리 정책을 지금 만들면
   운영 데이터 없이 보관 기간을 추측하게 된다. PRD가 정한 재검토 조건(볼륨 증가)이
   그 데이터를 기다리라는 뜻이다.

4. **저장 생성의 FK 레이스는 조건부 항목으로 남긴다.**
   `SavedTripService.save`는 코스 조회와 삽입이 별개 auto-commit이라, 그 사이에 코스가
   지워지면 FK 위반이 500 `INTERNAL_ERROR`로 나간다. 원인은 "없는 코스"이므로
   404 `COURSE_NOT_FOUND`가 맞다. **다만 코스 삭제 경로가 없어 지금은 재현되지 않는다.**
   삭제 경로가 생기는 변경에 이 매핑을 함께 넣는다. → [data-model.md](../data-model.md)

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 지금 만료(예: 30일)를 도입하고 정리 배치를 만든다 | 데이터가 무한히 쌓이지 않는다. 나중에 도입하면 이미 쌓인 데이터의 소급 적용을 정해야 한다 | PRD가 MVP 무기한으로 이미 정했다. 운영 데이터 없이 기간을 정하면 근거가 추측뿐이다. 저장된 코스 처리(외래키가 삭제를 막는 것)까지 함께 풀어야 해서 범위가 크다 |
| 만료 컬럼(`expires_at`)만 미리 넣고 NULL로 둔다 | 나중에 마이그레이션 없이 켤 수 있다 | 쓰지 않는 컬럼이 스키마와 문서에 의미를 요구한다. Flyway를 쓰므로 필요할 때 컬럼을 추가하는 비용이 낮다 |
| `saved_trips.course_id`를 `ON DELETE CASCADE`로 바꾼다 | 코스 정리가 저장 항목에 막히지 않는다 | 사용자가 저장한 항목이 서버 정리에 조용히 사라진다. 저장은 사용자가 명시적으로 한 행위다 |
| `saved_trips`에도 코스 스냅샷을 복사한다 | 코스를 지워도 저장 항목이 온전하다 | #31에서 한 번 구현했다 되돌린 선택이다. 목록이 무거워지고 항목별 역직렬화 실패 처리가 따라붙는다. `GET /courses/{courseId}`가 생겨 상세 조회 경로는 이미 닫혔다 |

## 결과

- 좋아지는 것:
  - Q-02가 닫히고 PRD·`data-model.md`·`requirements.md`가 한 방향을 가리킨다.
  - 삭제를 막는 동작이 의도된 정책으로 기록돼, 나중에 "실수로 빠진 `ON DELETE`"로 오해되지 않는다.
  - 코드와 스키마 변경이 없다. 되돌릴 것이 없다.
- 나빠지거나 감수하는 것:
  - **`courses`와 `shared_courses`가 계속 쌓인다.** 출시 전이라 실질적인 피해가 없다는 전제에 기대고 있다.
  - 공유 링크는 한번 나가면 회수할 수 없다. 공유 취소(`DELETE`) API가 없으므로
    잘못 공유했을 때 사용자가 되돌릴 방법이 없다. **MVP 범위 밖으로 둔다.**
  - `share_id`가 10자라 데이터가 쌓일수록 충돌 재시도가 잦아진다.
    ([data-model.md](../data-model.md)의 한계 항목) 만료가 없으니 이 압력은 줄지 않는다.

## 다시 검토해야 할 시점

- **볼륨이 늘어 저장 비용이나 `share_id` 충돌이 실제로 보일 때.** PRD가 적은 30일 기준이 출발점이다.
- **코스나 공유를 지우는 경로가 생길 때.** 그때 함께 정해야 하는 것:
  저장된 코스 처리(삭제를 계속 막을지), 위 4번의 FK 레이스 404 매핑, 공유 취소 API 여부.
- 로그인이 생겨 "내 공유 링크 목록"처럼 사용자가 직접 관리하는 화면이 생길 때.
