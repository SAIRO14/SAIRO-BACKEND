# 0003. Flyway로 스키마 관리

- **상태:** 수용됨
- **날짜:** 2026-07-23
- **관련:** 이슈 #18, PR #19

## 맥락

스키마가 `src/main/resources/db/schema.sql` 파일 하나였고 적용은 수동이었다.

문제는 이 구조가 **불일치를 감춘다**는 것이었다.

- `schema.sql`을 고쳐도 이미 떠 있는 로컬·운영 DB에는 반영되지 않았다.
- 테스트는 컨테이너를 매번 새로 만들어 최신 `schema.sql`을 적용하므로 **항상 통과**했다.
- 즉 실제 DB와 코드가 어긋나도 CI가 잡지 못했다. `ddl-auto: validate` 때문에
  그 불일치는 애플리케이션이 뜨지 않는 형태로 뒤늦게 드러난다.

저장 여행지 테이블 추가가 예정돼 있었고, PR #16도 `devices`·`analysis_history`를
추가하려던 참이라 여러 사람이 같은 파일을 동시에 고칠 상황이었다.

## 결정

**Flyway를 도입한다.** `db/schema.sql`을 `db/migration/V1__init_schema.sql`로 옮기고,
이후 변경은 새 `V<번호>__<설명>.sql` 파일로만 추가한다.

- `baseline-on-migrate: true`, `baseline-version: 1`
- 테스트 컨테이너도 initdb 대신 Flyway로 스키마를 만든다.
- 의존성은 `spring-boot-starter-flyway`를 쓴다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| Liquibase | XML·YAML로 DB 독립적 기술이 가능하고 롤백 기능이 있다 | PostgreSQL만 쓸 계획이라 추상화가 이득이 없다. SQL을 그대로 쓰는 쪽이 pgvector 확장이나 ivfflat 인덱스처럼 DB 고유 기능을 다루기 쉽다 |
| `ddl-auto: update` | 도구가 필요 없다 | 무엇을 어떻게 바꿀지 통제할 수 없고 이력이 남지 않는다. 운영 DB에 쓸 수 없다 |
| 지금처럼 두고 규칙으로 관리 | 변경이 없다 | 이미 실패하고 있던 방식이다. 사람이 기억하는 것에 의존한다 |

### baseline을 쓴 이유

팀원 로컬 DB와 운영 DB에는 V1의 테이블이 **이미 있다.**
이 상태에서 Flyway를 그냥 붙이면 기동 시 바로 실패한다.

대안으로 모두가 DB를 지우고 다시 만드는 방법이 있었지만,
적재해둔 사진·장소 데이터를 다시 넣어야 해서 비용이 크고 실수 여지가 있었다.

`baseline-on-migrate`는 테이블이 이미 있는 DB에서 V1을 실행하지 않고 기준선만 기록한다.
빈 DB에는 V1부터 정상 적용된다. 기존 DB를 건드리지 않아도 된다.

## 결과

**좋아지는 것**

- 스키마 변경이 파일로 남고 순서대로 자동 적용된다.
- 테스트 컨테이너가 Flyway로 스키마를 만들므로 **마이그레이션 자체가 CI에서 검증**된다.
- 여러 사람이 같은 파일을 고치는 대신 각자 새 파일을 추가하므로 충돌이 줄어든다.

**감수하는 것**

- 이미 적용된 마이그레이션 파일은 수정할 수 없다. 체크섬이 달라지면 검증에서 실패한다.
  잘못된 내용은 새 버전으로 바로잡아야 한다.
- 마이그레이션 번호가 사람 사이에 겹칠 수 있다. 동시 작업 시 조율이 필요하다.

**함정 하나**

`flyway-core`만 추가했을 때 **에러 없이 마이그레이션이 실행되지 않았다.**
의존성은 정상 해석됐지만 로그가 한 줄도 없었고 테이블이 만들어지지 않았다.

Spring Boot 4가 Flyway 자동 설정을 `spring-boot-autoconfigure`에서 분리한 것이 원인이었다.
`spring-boot-starter-flyway`를 써야 한다. 실패가 조용해서 놓치기 쉬워
`build.gradle`과 AGENTS.md에 이유를 남겼다.

**검증**

baseline 동작은 팀원들의 실제 DB에 영향을 주므로 `FlywayBaselineTest`로 고정했다.
별도 DB를 만들어 Flyway 도입 전 상태를 재현한 뒤, 적용된 마이그레이션이 0건이고
이력에 `BASELINE` 한 줄만 남는 것을 확인한다.

**뒤따라야 하는 작업**

- PR #16의 `devices`·`analysis_history` 추가분을 `V2__...sql`로 옮겨야 한다.
  `schema.sql` 수정으로 남아 있으면 파일이 사라져 충돌한다.

## 다시 검토해야 할 시점

무중단 배포에서 스키마 변경이 필요해지면, 하위 호환 마이그레이션 전략을 별도로 정해야 한다.
