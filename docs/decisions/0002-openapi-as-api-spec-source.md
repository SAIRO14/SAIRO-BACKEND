# 0002. OpenAPI를 API 명세 정본으로

- **상태:** 수용됨
- **날짜:** 2026-07-23
- **관련:** 이슈 #18, PR #19, PR #16

## 맥락

main 브랜치만 봐서는 API 계약을 알 수 없었다. springdoc은 머지되지 않은 PR #16에만 있었고,
저장소에 API 명세 문서도 없었다. 클라이언트가 API를 확인하려면 컨트롤러 코드를 직접 읽어야 했다.

곧 API가 4개 더 늘어날 예정이라(저장 여행지) 그 전에 명세를 어디서 관리할지 정해야 했다.

## 결정

**코드에서 생성되는 OpenAPI 문서를 API 명세의 정본으로 삼는다.**
엔드포인트별 요청·응답 스펙을 담은 별도 문서를 만들지 않는다.

- springdoc-openapi를 main에 도입한다.
- 컨트롤러에 `@Tag` `@Operation` `@ApiResponses` `@Parameter`를 채운다.
- **오류 응답에는 `ErrorCode` 이름을 함께 적는다.** 예: `404 — PLACE_NOT_FOUND`
- 전역 규칙(오류 코드 표, 멱등성, 페이지네이션)만 `docs/api-contract.md`에 둔다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| 손으로 쓴 마크다운 명세 | 서버를 안 띄워도 전체 API를 볼 수 있다. 배경 설명을 자유롭게 쓸 수 있다 | 구현과 이중 관리가 된다. 어긋나기 시작하면 **틀린 명세가 없는 명세보다 나쁘다**. 앞선 문서들이 이미 낡아 있던 게 근거였다 |
| OpenAPI JSON을 빌드 때 추출해 커밋 | 변경 이력이 diff로 남고 수기 작성이 아니라 어긋나지 않는다 | 생성물을 저장소에 두면 리뷰에 노이즈가 크게 늘고 머지 충돌이 잦다. 이력이 필요하면 나중에 도입할 수 있다 |
| 명세를 먼저 쓰고 코드를 생성 | 계약을 먼저 합의할 수 있다 | 이미 구현된 API가 7개 있어 지금 도입하면 역방향 작업이 크다 |

## 결과

**좋아지는 것**

- 명세와 구현이 어긋날 수 없다. 같은 소스에서 나온다.
- 클라이언트가 Swagger UI에서 오류 코드까지 확인하고 분기할 수 있다.
- API 추가 시 문서 갱신을 잊는 실수가 구조적으로 줄어든다.

**감수하는 것**

- 서버를 띄워야 명세를 볼 수 있다.
- 어노테이션이 컨트롤러 코드를 길게 만든다.
- **어노테이션을 부실하게 쓰면 명세도 부실해진다.** 강제할 장치가 없어서
  AGENTS.md에 작성 규칙을 명시하고 PR 체크리스트에 넣었다.

실제로 PR #16의 `DeviceController`에서 `@Tag` 설명은 "X-Device-Id로 식별"인데
구현은 경로 변수를 쓰는 불일치가 있었다. 어노테이션이 틀리면 명세도 틀린다는 사례다.
그래서 규칙에 "구현과 설명이 다른 어노테이션을 쓰지 않는다"를 넣었다.

**뒤따라야 하는 작업**

- PR #16과 springdoc 의존성·`SwaggerConfig`가 중복된다. 재조정이 필요하다.
  같은 버전(3.0.3), 같은 위치로 선언해 충돌을 줄여뒀다.

## 다시 검토해야 할 시점

클라이언트와 계약을 먼저 합의해야 하는 상황이 반복되면 스펙 우선 방식을 다시 본다.
