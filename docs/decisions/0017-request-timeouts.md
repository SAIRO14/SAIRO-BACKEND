# 0017. 요청 타임아웃과 외부 호출 예산

- **상태:** 수용됨
- **날짜:** 2026-08-07
- **관련:** 이슈 #34 (Q-09), #29, [ADR 0016](./0016-self-built-course-with-nearby-places.md), [api-contract.md §6](../api-contract.md#6-부분-실패-처리)

## 맥락

`requirements.md`는 "DB와 외부 API 타임아웃을 설정하고 무한 대기를 허용하지 않는다"를 요구하는데
**값이 정해지지 않았고 설정도 없었다.** Q-09로 열려 있던 항목이다.

코드를 열어보니 미결이 아니라 결함에 가까웠다.

- `TourApiClient`가 `RestClient.builder().baseUrl(baseUrl).build()`로 만들어진다.
  Spring Boot의 자동 구성 빌더가 아니라 **맨 빌더라 어떤 타임아웃도 붙지 않는다.**
  기반은 JDK `HttpClient`이고, 이 클라이언트의 기본 리드 타임아웃은 **무한**이다.
  TourAPI가 연결만 받고 응답하지 않으면 요청 스레드가 그대로 묶인다.
- `application.yaml`에 DB 타임아웃이 없다. 커넥션 획득(`connection-timeout`)도,
  쿼리 실행 상한도 설정돼 있지 않다.

[ADR 0016](./0016-self-built-course-with-nearby-places.md)으로 주변 장소 추천(B안)이 확정되면서
**코스를 조회할 때** TourAPI를 부르고 이미지가 없으면 Google Places를 한 번 더 거치는 구조가 됐다.
외부 호출이 2단이 되므로 이 항목을 닫기 전에 구현에 들어가면 무한 대기 경로가 더 늘어난다.

**타임아웃 값만으로는 부족하다.** 코스 1건이 장소 수만큼 TourAPI를 부르므로(최대 5회),
순차로 부르면 상한이 5배가 된다. **병렬 여부와 코스당 호출 상한을 함께 정해야 값이 의미를 갖는다.**

초과했을 때의 응답은 새로 정할 것이 없다. [api-contract.md §6](../api-contract.md#6-부분-실패-처리)이
이미 **"외부 API 실패도 그 항목만 빼고 나머지를 반환한다. 장소 상세는 TourAPI가 죽어도
DB 정보와 결측 표시로 응답한다"**로 정해두었다. 타임아웃은 그 "실패"의 한 종류다.

## 결정

MVP 기준값을 아래로 정한다. **성공률을 우선한 여유 있는 값**이다 — 데이터가 얇은 상태라
호출이 실패하면 화면이 비고, 지금은 느린 응답보다 빈 응답이 더 아프다.

| 대상 | 값 |
|---|---|
| TourAPI 커넥트 타임아웃 | **3초** |
| TourAPI 리드 타임아웃 | **5초** — 커넥트를 포함한 **시도 전체의 데드라인**이다 |
| TourAPI 재시도 | **1회.** 첫 시도가 **3초 안에** 실패했을 때만 (아래) |
| TourAPI `fetchDetail` 1회의 상한 | **8초** (재시도 판단 기준 3초 + 리드 타임아웃 5초) |
| DB 쿼리 실행 상한 | **5초** (PostgreSQL `statement_timeout`) |
| DB 커넥션 획득 상한 | **5초** (Hikari `connection-timeout`) |
| 코스 1건의 외부 호출 예산 | **10초**, 병렬 호출, **최대 5건** |
| 전체 응답 상한 — 취향 분석 | **15초** |
| 전체 응답 상한 — 코스 조회 | **12초** |

초과 시 응답은 §6을 그대로 따른다. **해당 장소만 결측으로 두고 `infoIncomplete: true`로 표시하며,
요청 전체를 500으로 실패시키지 않는다.** 새 오류 코드를 만들지 않는다.

### 재시도는 예외 종류가 아니라 남은 시간으로 판단한다

재시도 1회를 걸되, **첫 시도가 3초를 넘겨 실패했으면 재시도하지 않는다.**
예외 종류는 "다시 보내볼 가치가 있는가"만 가른다 — 5xx와 IO 오류는 순간적인 문제일 수 있지만
4xx는 같은 요청을 보내도 결과가 같다.

**실제 제약은 시간이다.** 리드 타임아웃 5초로 끝난 시도와, 5초를 끌다 500을 뱉은 시도는
**같은 비용을 쓴 것**이다. 한 번 더 보내면 그 한 건이 최악 10초를 써서 코스당 예산 10초를
혼자 먹는다. 느린 상대에게 부하를 더하는 쪽이기도 하다. 그러니 둘을 같게 다뤄야 한다.

> **처음에는 "리드 타임아웃만 재시도에서 뺀다"로 썼다가 고쳤다.**
> 4.9초를 끌다 503을 뱉는 과부하 서버는 흔한 형태인데, 예외 종류로 가르면 **그건 재시도한다.**
> 버리려던 비용을 정확히 그대로 쓰면서 근거만 비켜간다. 기준을 시간으로 바꾸면
> 두 경우가 같게 처리되고, 부수적으로 `HttpConnectTimeoutException`과
> `HttpTimeoutException`의 상속 순서에 의존하던 분기가 **사라진다.**

이 규칙이 한 호출에 상한을 준다. 한 시도가 리드 타임아웃(5초)을 넘지 못하고,
재시도는 경과 3초 이하일 때만 시작하므로 **`fetchDetail` 1회는 8초를 넘지 않는다.**

### DB 상한은 `statement_timeout`으로 건다

JPA의 `jakarta.persistence.query.timeout`이 아니라 **PostgreSQL 서버 측 `statement_timeout`**을
커넥션 속성으로 건다. 이 프로젝트는 JPA와 `JdbcTemplate`을 함께 쓰고
(`PhotoEmbeddingRepository`의 pgvector 조회가 `JdbcTemplate`이다),
JPA 힌트는 `JdbcTemplate` 경로를 덮지 못한다. 한 군데서 전부 덮으려면 서버 측이 맞다.

**Flyway는 이 상한에서 뺀다.** 그냥 두면 마이그레이션도 5초에 걸리고,
실패 모드가 **"운영 배포에서 앱이 뜨지 않는다"**이다.
`spring.flyway.url`을 주어 **Flyway가 자체 데이터소스를 쓰게 하고**,
거기에만 `init-sqls: ["SET statement_timeout = 0"]`을 건다.

> **데이터소스를 나누는 것이 핵심이다.** 같은 풀에 `init-sqls`만 걸면
> `SET`이 실행된 커넥션이 **풀로 돌아가** 이후 런타임 쿼리까지 상한 없이 돌게 된다.
> 세션 설정이라 커넥션에 남기 때문이다. 이 함정은 `DatabaseTimeoutTest`가 실제로 잡았다 —
> 처음에 같은 풀에 걸었을 때 `SHOW statement_timeout`이 `0`으로 나왔다.
> **그래서 그 테스트를 남겨 둔다.**

> 경고 주석으로 "무거운 마이그레이션은 `SET LOCAL`로 푸세요"라고 남기는 안을 먼저 썼다가 버렸다.
> **경고는 언젠가 안 읽힌다.** 게다가 pgvector 프로젝트에서 가장 나올 법한 무거운 작업인
> `CREATE INDEX CONCURRENTLY`는 트랜잭션 안에서 실행할 수 없어 `SET LOCAL`로 풀리지도 않는다
> (Flyway가 마이그레이션을 트랜잭션으로 감싼다). 설정 한 줄로 갈래 자체를 없앤다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| **보수적 값** (커넥트 2s / 리드 3s / 재시도 없음, 예산 6s) | 꼬리 지연이 짧다. 스레드가 빨리 풀린다 | 데이터가 얇아 결측이 곧 빈 화면이다. 지금 단계에서는 느린 응답보다 빈 응답이 더 아프다 |
| **타임아웃만 정하고 병렬·상한은 나중에** | 당장 할 일이 적다 | 순차 5회면 상한이 25초가 된다. 값을 정해도 실제 상한이 안 정해져 Q-09가 닫히지 않는다 |
| **JPA `jakarta.persistence.query.timeout`** | 설정 한 줄. Flyway에 영향 없음 | `JdbcTemplate` 경로(pgvector 조회)를 덮지 못한다. 정작 느릴 만한 쿼리가 그쪽이다 |
| **Hikari `connection-timeout`만 설정** | 가장 간단 | 그건 **커넥션 획득** 상한이지 쿼리 실행 상한이 아니다. 느린 쿼리는 그대로 통과한다. 다만 이 값 자체는 함께 설정했다 — 버린 것은 "그것만 쓰는 안"이다 |
| **재시도를 예외 종류로만 판단** (리드 타임아웃만 제외) | 코드가 단순하다. 시간을 재지 않아도 된다 | 느린 5xx가 리드 타임아웃과 같은 비용을 쓰는데 재시도된다. 버리려던 비용을 그대로 쓰면서 근거만 비켜간다 |
| **리드 타임아웃에도 재시도** | 일시적 지연을 한 번 더 흡수 | 한 건이 최악 10초를 써 코스당 예산을 혼자 소진한다. 느린 상대에게 부하만 더한다 |
| **마이그레이션 예외를 주석 경고로** | 설정이 안 늘어난다 | 경고는 안 읽힌다. 실패 모드가 "운영 배포에서 앱이 안 뜬다"이고 `CREATE INDEX CONCURRENTLY`는 안내한 `SET LOCAL`로 풀리지도 않는다 |
| **같은 풀에 Flyway `init-sqls`만 추가** | 설정 한 줄 | **런타임까지 상한이 풀린다.** `SET`이 걸린 커넥션이 풀로 돌아간다 |
| **타임아웃 초과 시 5xx** | 클라이언트가 실패를 명확히 안다 | [api-contract §6](../api-contract.md#6-부분-실패-처리)의 부분 실패 규칙과 어긋난다. TourAPI는 보완 정보라 없어도 화면이 성립한다 |

## 결과

- 좋아지는 것:
  - **무한 대기 경로가 닫힌다.** TourAPI가 응답하지 않아도 한 호출이 **최악 8초**에 끝난다
    (재시도를 포함한 값이다). 리드 타임아웃이 응답 바디 읽기까지 덮으므로
    "헤더만 주고 바디에서 멈추는 상대"도 여기서 끊긴다.
  - #29(장소 상세 TourAPI 보완)와 주변 장소 추천(B안) 구현이 **풀린다.** Q-09가 유일한 차단이었다.
- 나빠지거나 감수하는 것:
  - 느린 TourAPI 응답을 기다리다 버리는 만큼 **평상시 지연이 늘 수 있다.**
  - **요청 전체의 상한은 아직 없다.** `statement_timeout`은 쿼리 **1건**의 상한이라
    한 요청이 N번 질의하면 N×5초가 가능하다. 여기서 닫은 것은 **외부 호출 쪽 무한 대기**다.
  - 5xx 재시도에 간격이 없다. 1회뿐이고 빠르게 실패한 경우에만 재시도하므로 감수한다.
  - 값은 **관측 없이 정한 추정치다.** 운영 지표가 쌓이기 전까지는 근거가 얇다.
- 이 결정에 뒤따라야 하는 작업:
  - `TourApiClient`에 커넥트·리드 타임아웃과 재시도 적용 — **이 PR**
  - `application.yaml`에 `statement_timeout` — **이 PR**
  - **병렬 호출과 코스당 5건 상한은 아직 구현하지 않았다.** 지금 TourAPI를 부르는 곳은
    `GET /places/{spotId}` 하나뿐이라 호출이 1건이다. 여러 건을 부르는 코드가 생기는
    #29 / 주변 장소 구현에서 이 값대로 넣는다.
  - 전체 응답 상한(15초 / 12초)도 **아직 강제하지 않는다.** 개별 타임아웃의 합이 그 아래라
    지금은 넘길 수 없다. 호출이 늘어나면 상위에서 예산으로 잘라야 한다.

## 다시 검토해야 할 시점

- 운영 지표가 쌓여 TourAPI 응답 시간 분포를 알게 됐을 때. **p99 기준으로 값을 다시 잡는다.**
- 주변 장소 추천(B안)이 구현돼 외부 호출이 2단이 됐을 때. Google Places 몫의 예산이 필요하다.
- 코스당 장소 수(Q-05, #51)가 5보다 커질 때. 호출 상한 5건이 그 값에 묶여 있다.
