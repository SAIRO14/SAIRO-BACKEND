# 0001. 오류 응답 계약 표준화

- **상태:** 수용됨
- **날짜:** 2026-07-23
- **관련:** 이슈 #18, PR #19

## 맥락

오류가 나면 `{"error": "장소를 찾을 수 없습니다."}` 형태로 메시지 하나만 반환했다.

이 형태로는 클라이언트가 할 수 있는 게 없었다.

- 오류 종류로 분기하려면 한국어 문자열을 파싱해야 한다. 메시지를 다듬는 순간 깨진다.
- 재시도해도 되는 상황인지 알 수 없다. 공통 오류 화면의 `재시도` 버튼을 언제 보여줄지 판단할 근거가 없었다.
- 사용자가 오류를 신고해도 서버 로그에서 해당 요청을 찾을 방법이 없었다.

서비스 계층은 `ResponseStatusException`에 HTTP 상태 코드를 직접 넣고 있었다.
비즈니스 로직이 전송 계층의 표현을 알아야 했고, 같은 원인의 오류가 호출 지점마다
다른 상태 코드로 나갈 여지가 있었다.

곧 시작할 저장 API는 중복 저장에 409를 써야 해서, 상태 코드를 처음으로 본격적으로
구분해야 하는 기능이었다. 그 전에 형식을 정하지 않으면 API마다 계약이 갈릴 상황이었다.

## 결정

모든 오류 응답을 아래 한 가지 형태로 통일한다.

```json
{
  "code": "ANALYSIS_NOT_FOUND",
  "message": "분석 결과를 찾을 수 없습니다.",
  "retryable": false,
  "traceId": "3f8c1a20b4d1"
}
```

- 상태 코드·메시지·재시도 가능 여부는 `common/ErrorCode` enum이 한곳에서 결정한다.
- 서비스 계층은 `BusinessException(ErrorCode)`만 던진다. HTTP 상태 코드를 알지 못한다.
- 요청마다 `TraceIdFilter`가 추적 ID를 발급해 MDC와 `X-Trace-Id` 헤더에 넣는다.
- 기존 API에도 **일괄 적용**한다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| RFC 7807 (`application/problem+json`) | 표준이라 도구 지원이 있다 | `type` URI를 운영할 계획이 없고 `retryable`은 결국 확장 필드로 넣어야 한다. 표준을 절반만 따르면 표준의 이점이 없다 |
| 상태 코드만 쓰고 본문은 메시지만 | 지금 구조를 안 바꿔도 된다 | 404 하나로 "분석 없음"과 "장소 없음"을 구분할 수 없다. 클라이언트가 엔드포인트별로 분기해야 한다 |
| 신규 API만 적용, 기존은 점진 전환 | 변경 범위가 작다 | 두 형식이 공존하면 클라이언트가 양쪽을 모두 처리해야 한다. 전환할 코드가 7곳뿐이라 미룰 이유가 없었다 |
| `retryable` 없이 상태 코드로 판단 | 필드가 하나 준다 | 500이어도 재시도가 무의미한 경우가 있고 404여도 재시도가 유효한 경우가 있다. 서버가 아는 것을 클라이언트가 추측하게 만들 이유가 없다 |

## 결과

**좋아지는 것**

- 클라이언트가 `code`로 분기하고 `retryable`로 재시도 UI를 결정할 수 있다.
- 사용자가 오류 화면을 캡처해 보내면 `traceId`로 해당 로그를 바로 찾을 수 있다.
- 오류 코드 목록이 `ErrorCode` 한 파일에 모여 Swagger 명세와 대조하기 쉽다.
- 서비스 계층이 HTTP를 몰라도 된다.

**감수하는 것**

- 오류가 늘 때마다 `ErrorCode`에 항목을 추가해야 한다. 코드가 화면 단위로 늘어나면
  관리가 어려워지므로 **원인 단위로만 만든다**는 규칙을 함께 뒀다.
- 기존 API의 응답 형태가 바뀌므로 클라이언트 대응이 필요하다.
- **호환성이 깨지는 변경이 하나 있다.** 존재하지 않는 `analysisId` 응답이 400에서
  404(`ANALYSIS_NOT_FOUND`)로 바뀐다. 리소스 부재는 404라는 기준에 맞춘 것이다.

**뒤따라야 하는 작업**

- 클라이언트에 형식 변경과 `analysisId` 404 변경을 공유한다.
- `ResponseStatusException`이 새로 들어오지 않는지 확인한다. 전역 핸들러에 방어선을 남겨뒀지만
  임시 대응이다.

## 다시 검토해야 할 시점

외부에 API를 공개하게 되면 RFC 7807 준수를 다시 검토한다.
서드파티 도구 호환이 필요해지는 시점이다.
