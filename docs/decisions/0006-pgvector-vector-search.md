# 0006. pgvector 벡터 유사도 검색

- **상태:** 수용됨
- **날짜:** 2026-07-23
- **관련:** 이슈 #39

## 맥락

CLIP 임베딩으로 변환된 2,200장의 여행 사진 벡터를 저장하고, 사용자 취향 벡터와 코사인 유사도를 기준으로 빠르게 유사 사진을 검색해야 한다. 취향 분석 목표 응답 시간은 3초 이내다.

## 결정

PostgreSQL 확장인 pgvector를 사용해 벡터 저장과 유사도 검색을 처리한다. 이미 운영 중인 PostgreSQL에 `CREATE EXTENSION vector`만으로 활성화한다.

## 고려한 대안

| 대안 | 장점 | 버린 이유 |
|---|---|---|
| Milvus / Weaviate | 수억 건 이상 대규모 벡터 특화, ANN 인덱스 성숙 | 별도 인프라 운영 필요, 2,200건 규모에서 과도한 복잡도 |
| Elasticsearch dense_vector | 텍스트 검색과 통합 가능 | 이미 PostgreSQL 사용 중, 추가 인프라 부담 |
| Redis Vector Search | 인메모리 속도 | 영속성·트랜잭션 보장 약함, 운영 비용 |
| 애플리케이션 레이어 계산 | 의존성 없음 | 2,200건이라도 매 요청마다 전체 순회는 응답 시간 초과 위험 |

## 결과

- 좋아지는 것: 기존 PostgreSQL 인프라 재사용, 별도 벡터 DB 없음, Flyway로 스키마 관리 일원화
- 나빠지거나 감수하는 것: 수십만 건 이상으로 데이터가 늘면 인덱스 튜닝 또는 전용 벡터 DB 이전 필요
- 이 결정에 뒤따라야 하는 작업: `CREATE EXTENSION vector` Flyway 마이그레이션, `photo_embeddings` 테이블에 `vector(512)` 컬럼 추가, IVFFlat 인덱스 생성

## 다시 검토해야 할 시점

- 벡터 데이터가 수십만 건을 초과할 때
- 유사도 검색 응답 시간이 3초를 넘을 때
