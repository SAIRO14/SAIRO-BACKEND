# 백엔드 요구사항

백엔드가 보장해야 하는 동작만 정리한다. 화면 전환, 모션, 앱 로컬 저장 등
클라이언트 영역은 다루지 않는다.

미결 항목은 여기 적지 않는다. [open-questions.md](./open-questions.md)를 참조한다.

## 1. 제품 한 줄 요약

사용자가 **장소 정보를 보지 않고** 관광 사진 5~10장을 고르면, 사진의 분위기와 어울리는
**국내 지역**과 **1박 2일 코스**를 추천한다. 로그인 없이 기기 단위 익명 식별자로 동작한다.

```text
사진 풀 조회 → 취향 분석 → 지역 추천 → 코스 생성 → 저장 / 공유
```

## 2. 백엔드가 지켜야 하는 제약

이 네 가지는 제품의 정체성이라 협상 대상이 아니다.

| 제약 | 의미 |
|---|---|
| **선택 단계 정보 은닉** | 사진 풀 응답에 장소명·지역명·관광지명·촬영지·분위기 태그·임베딩을 넣지 않는다. 추천 결과에서 처음으로 지역을 공개한다. |
| **추천 단위는 지역** | 개별 장소가 아니라 지역을 추천한다. 같은 지역이 중복 카드로 나오면 안 된다. |
| **익명 사용자 격리** | 다른 익명 사용자의 저장 목록에 접근할 수 없어야 한다. 소유자 조건 없는 조회 쿼리를 만들지 않는다. |
| **외부 장애 격리** | TourAPI 장애가 장소 상세 요청 전체의 실패로 번지면 안 된다. |

## 3. 기능별 요구사항

### 3.1 사진 풀

- 한 세션에 사용할 사진을 무작위로 반환한다. 기본 40장이다.
- 응답에는 사진 ID와 이미지 URL만 담는다.
- 필요한 개수만 조회한다. 전체를 읽고 잘라내지 않는다.

### 3.2 취향 분석

- 사진 ID **5~10개**를 받는다. 이 범위는 클라이언트와 서버 양쪽에서 검증한다.
- 중복 ID를 제거한 고유 장수가 5 미만이면 400이다.
- 유효하지 않은 ID가 섞여 있을 때는 유효한 것으로 진행하되, 유효 장수가 5 미만이면 400이다.
- 유효한 선택 사진 임베딩의 **산술 평균**을 대표 임베딩으로 쓴다.
- 선택 사진 키워드 빈도 **상위 5개**를 분위기 태그 후보로 삼는다. 화면에는 최대 3개가 표시된다.
- 응답은 분석 ID, 분위기 태그, 요약 문장을 포함한다. 분석 ID는 추천 조회에 사용한다.
- 분석 임시 저장소는 TTL과 최대 크기를 가져야 하며, 서버를 재시작하거나 인스턴스가 여러 개여도
  유효한 분석 ID가 일관되게 동작해야 한다.

> 현재 구현은 프로세스 메모리 `ConcurrentHashMap`이라 이 요구를 만족하지 못한다. → [Q-06](./open-questions.md)

### 3.3 지역 추천

- 대표 임베딩과 코사인 거리가 가까운 사진을 검색하고, 유사 사진의 지역 빈도로 상위 지역을 뽑는다.
- 광역 단위 문자열 정규화가 필요하다.
- 한 지역에 장소가 **2개 이상** 확보된 경우에만 코스 생성 대상으로 쓴다.
- 결과는 최대 3개 지역이며, 가능한 결과가 적으면 있는 것만 반환한다. 0개도 정상 응답이다.
- 추천 점수와 내부 정렬 기준은 응답에 노출하지 않는다.

지역 카드에 담기는 정보는 지역 ID, 지역명, 대표 이미지, 자유 문장 형태의 추천 이유,
대표 장소 최대 2개, 현재 사용자의 저장 여부다.

계산 방식은 [recommendation.md](./recommendation.md)에 있다.

### 3.4 장소 상세

- DB 정보를 우선 사용하고, **결측 필드별로** TourAPI를 호출해 보완한다.
- 보완 후에도 비어 있는 항목은 결측임을 응답에 표시한다.
- DB와 외부 API 모두 타임아웃을 설정하고 무한 대기를 허용하지 않는다.

### 3.5 코스 생성

- 지역과 장소 목록으로 Day 1과 Day 2를 만든다. 1박 2일 고정이다.
- 좌표가 있는 장소는 가까운 순서가 되도록 배치하고, 좌표가 없는 장소는 뒤로 보낸다.
- Day 1과 Day 2의 장소 수 차이는 **1개 이하**여야 한다.
- 요청의 지역과 실제 장소의 지역이 일치하는지 검증한다. 지역 밖 장소가 섞이면 안 된다.

### 3.6 저장 여행지

- 저장 단위는 **추천 지역과 그 시점의 코스 스냅샷**이다.
- 같은 추천 결과는 중복 저장할 수 없다. 같은 지역이라도 **코스가 다르면 별도 저장**한다.
- 목록은 최근 저장순이며 커서 기반 페이지로 조회한다. 전체 조회하지 않는다.
- 일부 항목이 손상되어 읽을 수 없으면 **해당 항목만 제외**하고 나머지 목록은 정상 반환한다.
- 저장 해제는 소유한 항목만 삭제한다. 남의 항목은 지워지지 않되 **응답으로 구분되지 않는다.**
  → [api-contract.md §4](./api-contract.md#4-소유권과-멱등성)
- 저장 생성과 해제는 중복 요청에 안전해야 한다.
- 추천 카드와 상세에 현재 사용자의 저장 여부를 제공한다.

### 3.7 공유

- 공유 버튼을 누른 시점의 지역과 코스를 읽기 전용 스냅샷으로 저장한다.
- 공유 링크 조회 결과는 **공유 당시 데이터와 동일**해야 한다.
- 공유 상세는 편집과 삭제를 제공하지 않는다.
- 공유 생성은 중복 요청에 안전해야 하고, 공유 ID가 충돌하면 재생성한다.
- 공유 링크에 내부 DB ID나 익명 사용자 ID를 직접 노출하지 않는다.

## 4. API 목록

엔드포인트별 요청·응답 상세는 Swagger를 본다. 여기서는 존재해야 하는 기능만 적는다.

| 기능 | Method | URI | 상태 |
|---|---|---|---|
| 사진 풀 | GET | `/photos?limit=40` | 구현됨 |
| 취향 분석 | POST | `/taste-analysis` | 구현됨 |
| 추천 조회 | GET | `/recommendations?analysisId={id}` | 구현됨 |
| 장소 상세 | GET | `/places/{spotId}` | 구현됨 |
| 코스 생성 | POST | `/courses` | 구현됨 |
| 코스 공유 | POST | `/courses/{courseId}/share` | 구현됨 |
| 공유 조회 | GET | `/courses/shared/{shareId}` | 구현됨 |
| 저장 생성 | POST | `/saved-trips` | 구현됨 |
| 저장 목록 | GET | `/saved-trips?cursor={커서}&size=20` | 구현됨 |
| 저장 해제 | DELETE | `/saved-trips?savedTripId={id}` | 구현됨 |

익명 사용자 ID는 `X-Device-Id` 헤더로 받는다. → [api-contract.md §4](./api-contract.md#4-소유권과-멱등성)
저장 목록이 커서를, 저장 해제가 `savedTripId`를 경로가 아니라 쿼리 파라미터로 받는 것이 이 제약 때문이다.

**이 제약에 딸린 비용이 하나 있다.** 쿼리 스트링은 액세스 로그·프록시·브라우저 히스토리에
기본적으로 남는다. 경로에서 뺀 식별자가 그쪽으로 흘러가므로, 노출 자리를 옮긴 것이지 없앤 것은 아니다.
`savedTripId`는 소유권 판정의 대상이지 익명 사용자 ID가 아니라서
"로그에 남기지 않는다"(§5 보안)에 걸리는 값은 아니다.
제약 자체를 다시 볼 때 이 비용도 함께 본다.

## 5. 비기능 요구사항

### 보안과 개인정보

- TourAPI 키와 DB 비밀번호는 환경 변수 또는 추적되지 않는 로컬 설정으로만 관리한다.
- **로그에 API 키, 익명 사용자 ID 원문, 전체 임베딩을 남기지 않는다.**
- 사진 임베딩과 원본 데이터 파일은 API로 공개하지 않는다.

### 성능

- 임베딩 검색은 인덱스를 사용한다.
- 저장 목록은 커서 페이지로만 조회한다.
- 대표 이미지 URL 하나가 실패해도 API 전체가 실패하지 않아야 한다.

## 6. 구현이 요구사항에 못 미치는 지점

작업 우선순위 판단용이다. 해결되면 이 표에서 지운다.

| 우선순위 | 영역 | 현재 | 필요한 변경 |
|---|---|---|---|
| P0 | 분석 저장 | 프로세스 메모리, TTL 없음 | TTL 있는 공유 저장소로 교체 |
| P1 | 장소 보완 | 정보 하나만 있어도 완전하다고 판단 | 결측 필드별로 TourAPI 보완 |
| P2 | 데이터 import | 절대 경로와 DB 비밀번호 하드코딩 | CLI 인자와 환경 변수 사용 |
| P2 | 코스 정리 | `courses`와 `shared_courses`가 계속 쌓임 | 만료·정리 정책 (→ [Q-02](./open-questions.md)) |

**완료된 항목:** 오류 계약 표준화([ADR 0001](./decisions/0001-error-response-contract.md)),
스키마 마이그레이션([ADR 0003](./decisions/0003-flyway-for-schema-migration.md)),
코스 영속화와 공유 연결·지역 스냅샷·코스 지역 검증([ADR 0010](./decisions/0010-course-persistence.md)),
`X-Device-Id` 헤더 해석·검증([ADR 0007](./decisions/0007-anonymous-device-id.md), [api-contract §4](./api-contract.md#4-소유권과-멱등성)),
사진 풀 응답 `location` 제거, 취향 분석 선택 검증 5~10장,
추천 응답 지역 카드 구조 변경 (RegionCard · 장소 2개 미만 지역 제외 · 대표 장소 2개 미리보기 · 추천 이유),
저장 여행지 생성과 중복 판정([ADR 0011](./decisions/0011-saved-trip-identity.md)),
저장 목록 커서 페이지([api-contract §5](./api-contract.md#5-커서-페이지네이션)),
코스 소유권([ADR 0012](./decisions/0012-course-ownership.md)),
추천 카드 저장 상태 반영 (`X-Device-Id` 헤더 기준, 헤더 없으면 `saved: false`).

## 7. MVP 완료 조건

- 사진 선택 화면과 API에서 장소 정보가 노출되지 않는다.
- 5~10장 선택 규칙이 클라이언트와 서버 양쪽에서 검증된다.
- 추천 응답이 지역 카드 단위이며 상세 코스까지 연결된다.
- 저장 생성·목록·해제가 익명 사용자별로 동작한다.
- 공유 링크가 공유 당시 스냅샷을 재현한다.
- 핵심 API 통합 테스트와 오류 케이스 테스트가 CI에서 통과한다.

## 8. MVP 제외 범위

회원가입·로그인, GPS·알림 권한, 개별 관광지 상세 화면, 혼잡도, 연관 관광지,
사진 카테고리 필터, 추천 결과 편집, 모바일 웹 공유 상세, 공유 횟수와 행동 분석 로그.
