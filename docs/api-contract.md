# API 계약 규칙

모든 API에 공통으로 적용되는 규칙이다.

**엔드포인트별 요청·응답 스펙은 여기 없다.** 그건 Swagger가 정본이다
([ADR 0002](./decisions/0002-openapi-as-api-spec-source.md)).
이 문서는 코드 한 곳만 봐서는 드러나지 않는 전역 규칙을 다룬다.

- Swagger UI — `/swagger-ui.html`
- OpenAPI JSON — `/v3/api-docs`

## 1. 명명과 형식

- JSON 필드는 lower camel case를 쓴다.
- 시간 값은 ISO-8601 문자열로 주고받는다.
- 목록 응답에 아직 페이지 정보가 필요 없다면 배열을 그대로 반환한다.
  커서 페이지가 필요한 목록은 §5를 따른다.

## 2. 상태 코드

| 상황 | 코드 | 오류 코드 |
|---|---|---|
| 성공 | 200 | - |
| 생성됨 | 201 | - |
| 잘못된 입력 | 400 | `INVALID_REQUEST` 등 |
| 리소스 없음 또는 만료 | 404 | 도메인별 `*_NOT_FOUND` |
| 존재하지 않는 경로 | 404 | `ENDPOINT_NOT_FOUND` |
| 허용되지 않은 메서드 | 405 | `METHOD_NOT_ALLOWED` |
| 지원하지 않는 Content-Type | 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 충돌 | 409 | `SAVED_TRIP_CONFLICT` 등 (현재 쓰이는 곳 없음, §4 참고) |
| 서버 오류 | 500 | `INTERNAL_ERROR` 등 |

**프로토콜 수준 오류는 표준 HTTP 의미를 유지한다.** 405와 415를 400으로 뭉뚱그리지 않는다.
중간 프록시와 클라이언트가 원인을 구분할 수 없게 되기 때문이다.
405 응답에는 `Allow` 헤더를 함께 보낸다.

**리소스가 없는 것과 입력이 잘못된 것을 구분한다.** 형식이 맞는 ID인데 대상이 없으면 404이고,
형식 자체가 틀렸으면 400이다.

**형식을 검증할지는 값이 어디 실려 왔는지가 아니라 검증하지 않았을 때 무엇이 나가는지로 정한다.**
기준은 하나다 — **틀린 형식을 흘려보내면 거짓 응답이 나가는가.**
([ADR 0013](./decisions/0013-id-format-validation.md))

- **거짓 응답이 나가면 400이다.** 서버가 발급한 ID는 소문자 UUID v4인데,
  이 값들이 담긴 컬럼은 `TEXT`라 조회가 대소문자를 구분한다. 대문자 UUID를 흘려보내면
  조회가 빗나가 **실재하는 리소스를 두고 "없다"고 답하거나, 아무것도 지우지 않고 "지웠다"고 답한다.**
  `POST /saved-trips`의 `courseId`, `DELETE /saved-trips`의 `savedTripId`,
  `POST /courses/{courseId}/share`의 `courseId`가 여기 해당한다.
  **마지막 것은 경로에 있지만 검증한다.** 위치가 기준이 아니기 때문이다.
- **거짓이 나갈 게 없으면 검증하지 않고 404로 답한다.** 읽기 전용 조회가 여기 해당한다.
  `GET /courses/shared/{shareId}`가 그렇다. 없는 것을 없다고 답하는 것뿐이라
  형식을 따로 거르지 않아도 응답이 정직하다.

한때 "경로 ID는 형식을 검증하지 않는다"를 예외로 두고 근거를 **형식 노출**에서 찾았으나
그 근거는 성립하지 않는다. 유효한 형식은 Swagger `example`과 생성 API 응답으로 이미 공개돼 있어
탐색해서 알아낼 것이 없다. 반면 검증하지 않아서 나가는 거짓 응답은 실재하는 비용이었다.

**존재하지 않는 것과 만료된 것을 응답에서 구분하지 않기로 했다.** 공유 ID나 분석 ID가
만료됐는지 없는지 알려주면 유효한 ID를 탐색할 여지가 생긴다. 둘 다 404에 같은 코드로 답한다.

## 3. 오류 응답

모든 오류는 이 형태다. 근거는 [ADR 0001](./decisions/0001-error-response-contract.md)에 있다.

```json
{
  "code": "ANALYSIS_NOT_FOUND",
  "message": "분석 결과를 찾을 수 없습니다.",
  "retryable": false,
  "traceId": "3f8c1a20b4d1"
}
```

| 필드 | 의미 |
|---|---|
| `code` | 클라이언트 분기 기준. `common/ErrorCode` enum 이름과 1:1로 대응한다. |
| `message` | 사람이 읽는 설명. 그대로 사용자에게 노출하는 문구가 아니다. |
| `retryable` | **같은 요청을 그대로 재시도해서 성공할 가능성이 있는가.** 공통 오류 화면의 `재시도` 노출 판단에 쓴다. |
| `traceId` | 응답 헤더 `X-Trace-Id`와 같은 값. 서버 로그와 대조할 수 있다. |

`retryable`은 입력 오류와 리소스 부재에서 `false`다. 몇 번을 보내도 결과가 같기 때문이다.
일시적 장애나 외부 API 실패에서 `true`다.

### 오류 코드 목록

정본은 `common/ErrorCode`다. 코드를 추가하거나 바꿀 때는 그 enum을 고친다.
Swagger의 각 엔드포인트에도 발생 가능한 코드가 적혀 있다.

| 영역 | 코드 |
|---|---|
| 공통 | `INVALID_REQUEST` `RESOURCE_NOT_FOUND` `INTERNAL_ERROR` `INVALID_CURSOR` |
| 프로토콜 | `ENDPOINT_NOT_FOUND` `METHOD_NOT_ALLOWED` `UNSUPPORTED_MEDIA_TYPE` `NOT_ACCEPTABLE` |
| 디바이스 식별 | `DEVICE_ID_REQUIRED` `DEVICE_ID_INVALID` |
| 사진 풀 | `PHOTO_POOL_UNAVAILABLE` |
| 취향 분석 | `INVALID_PHOTO_SELECTION` `ANALYSIS_FAILED` `ANALYSIS_NOT_FOUND` |
| 추천 | `RECOMMENDATION_FAILED` |
| 장소 | `PLACE_NOT_FOUND` |
| 코스 | `INSUFFICIENT_SPOTS` `COURSE_NOT_FOUND` `COURSE_REGION_MISMATCH` |
| 공유 | `SHARE_CREATION_FAILED` `SHARED_COURSE_NOT_FOUND` |
| 저장 여행지 | `SAVED_TRIP_NOT_FOUND` `SAVED_TRIP_CONFLICT` `SAVED_TRIP_FORBIDDEN` |
| 외부 연동 | `EXTERNAL_API_FAILED` |

저장 여행지의 세 코드는 정의만 되어 있고 아직 어느 엔드포인트도 던지지 않는다.
**이유는 코드마다 다르다.** 셋 다 근거는 §4에 있다.

- `SAVED_TRIP_CONFLICT` — **저장 생성**이 멱등이라 충돌로 볼 상황 자체가 정의되지 않는다.
  같은 내용을 다시 저장하면 기존 항목을 그대로 반환한다.
- `SAVED_TRIP_NOT_FOUND` — **저장 해제**가 멱등이라 이미 없는 항목을 지워도 204다.
- `SAVED_TRIP_FORBIDDEN` — **저장 해제**가 남의 항목을 없는 항목과 구분하지 않아 이때도 204다.

### 코드를 새로 만드는 기준

**원인 단위로 만든다. 화면 단위로 만들지 않는다.** `SAVE_SCREEN_ERROR` 같은 이름은
같은 원인을 여러 코드로 쪼개고, 화면이 바뀌면 곧바로 낡는다.

## 4. 소유권과 멱등성

### 익명 사용자 식별

로그인이 없으므로 사용자는 기기가 만든 익명 식별자로만 구분한다.
근거는 [ADR 0007](./decisions/0007-anonymous-device-id.md)에 있다.

| 항목 | 내용 |
|---|---|
| 전달 위치 | 요청 헤더 `X-Device-Id` |
| 값 형식 | UUID v4 정규형(8-4-4-4-12). 앱 최초 실행 시 클라이언트가 생성해 기기에 보관한다 |
| 누락 | 400 `DEVICE_ID_REQUIRED` |
| 형식 오류 | 400 `DEVICE_ID_INVALID` |

- 소유자가 있는 데이터를 다루는 요청(코스 조회·저장 생성·목록·해제·상태 조회)에서 **필수**다.
- 저장 여부만 함께 내려주는 요청(추천 조회, 장소 상세)에서는 선택이다.
  헤더가 없으면 저장 여부를 `false`로 채우고 나머지는 정상 응답한다.
- **값이 비어 있는 헤더는 없는 것과 같게 다룬다.** 필수인 곳에서는 `DEVICE_ID_REQUIRED`다.
- 값의 **앞뒤 공백은 제거하고 판정**한다.
- **헤더가 두 번 이상 오면 400 `DEVICE_ID_INVALID`다.** 이 값은 소유권 판정의 입력이므로
  첫 값을 조용히 고르지 않는다.
- **선택인 곳이라도 형식이 틀리면 400이다.** 조용히 무시하면 클라이언트가
  저장 여부가 늘 `false`인 이유를 알 수 없다.
- 서버는 값을 **소문자로 정규화**해 사용한다. 대소문자만 다른 값은 같은 기기다.
- 버전이 4가 아닌 UUID는 받지 않는다.
- **헤더 값을 로그에 남기지 않는다.** (§7)

구현은 `common/DeviceIdArgumentResolver`가 한 곳에서 담당한다. 컨트롤러는 `@DeviceId`를
붙인 파라미터로 받는다. 필수 여부는 타입이 정한다 — `String`이면 필수,
`Optional<String>`이면 선택이다.

OpenAPI에는 `SwaggerConfig`가 헤더 파라미터와 `DEVICE_ID_*` 400 응답을 함께 붙인다.
**컨트롤러의 `@ApiResponses`에 이 400을 다시 적지 않는다.** 다른 이유로 400을 이미
선언했다면 `SwaggerConfig`가 그 설명 뒤에 디바이스 오류 코드를 이어 붙인다.

한 상태 코드에 원인이 둘 이상인 것은 정상이므로 **둘 다 명세에 남아야 한다.**
예전에는 컨트롤러가 선언한 400이 있으면 그대로 두고 돌아가 `DEVICE_ID_*`가 사라졌다.
`OpenApiContractTest.deviceIdEndpoints_documentDeviceIdErrorCodes`가 이 회귀를 막는다.

### 소유권

익명 사용자의 데이터를 다루는 모든 조회·삭제는 **소유자 조건을 쿼리에 포함**한다.
애플리케이션 코드에서 걸러내는 방식은 쓰지 않는다.

**남의 리소스에 접근하면 403이 아니라 404로 답한다.** 403은 "그 ID가 존재한다"는 사실을
알려주기 때문이다. `SAVED_TRIP_FORBIDDEN`이 404 상태를 갖는 이유다.

이 규칙이 지키려는 것은 상태 코드 404가 아니라 **"존재를 알려주지 않는다"** 쪽이다.
그래서 성공이 실패와 구분되지 않는 자리에서는 404조차 쓰지 않는다.
저장 해제가 그렇다. 남의 항목만 404로 답하면 없는 ID는 성공, 있는 ID는 404가 되어
`savedTripId`를 바꿔가며 실재 여부를 알아낼 수 있다. 아래 멱등성 항목을 함께 본다.

소유자가 있는 리소스는 **코스**(`courses.device_id`)와 **저장 여행지**(`saved_trips.device_id`)다.
코스를 만들면 그 기기가 소유자가 되고, 코스 조회·공유 생성·저장 생성은 소유자만 할 수 있다.
남의 코스는 404 `COURSE_NOT_FOUND`다. ([ADR 0012](./decisions/0012-course-ownership.md))

**공유 링크 조회(`GET /courses/shared/{shareId}`)는 소유자를 보지 않는다.**
공유는 남에게 보내라고 만든 것이라 소유자 개념이 없다. `shareId`를 아는 사람이 볼 수 있는 사람이다.

식별자를 URL 경로에 노출하지 않는다. 경로에 있으면 값을 바꿔가며 남의 데이터를 조회할 수 있다.

### 멱등성

저장 생성, 저장 해제, 공유 생성은 중복 요청에 안전해야 한다. 네트워크 재시도나
사용자의 연속 탭으로 같은 요청이 두 번 도착할 수 있다.

- **저장 생성** — 이미 같은 내용이 저장돼 있으면 새로 만들지 않고 기존 항목을 반환한다.
  같은 내용의 판정 키는 `(익명 사용자 ID, 코스 지문)`이다
  ([ADR 0011](./decisions/0011-saved-trip-identity.md)).
  이 키가 같으면 스냅샷의 순서·표시 정보 차이는 중복 판정에서 무시하고 최초 저장 스냅샷을 유지한다.
  충돌로 볼 상황이 정의되지 않으므로 **`SAVED_TRIP_CONFLICT` 409는 현재 발생하지 않는다.**
  코드는 정의만 남아 있고 저장 생성 엔드포인트에 문서화하지 않는다.
- **저장 해제** — 지울 것이 없어도 성공(`204`)으로 응답한다. 세 경우가 모두 같은 응답이다.
  내 항목을 지웠을 때, 이미 지워진 항목을 다시 지웠을 때, **남의 항목을 지우려 했을 때**다.
  앞의 둘은 재시도 안전성 때문이고, 남의 항목까지 여기 묶은 것은 존재를 감추기 위해서다(위 소유권).
  소유자 조건은 쿼리에 있어 남의 항목은 실제로 지워지지 않는다.
  이 엔드포인트는 지운 행 수를 응답에 담지 않는다. 담으면 구분이 되살아난다.
  따라서 **`SAVED_TRIP_NOT_FOUND` 404와 `SAVED_TRIP_FORBIDDEN` 404는 저장 해제에서 발생하지 않는다.**
- **공유 생성** — 한 코스의 공유 링크는 하나다. 이미 공유된 코스면 새로 만들지 않고
  기존 `shareId`를 반환한다. `share_id`가 충돌하면 재생성한다.

## 5. 커서 페이지네이션

저장 목록처럼 계속 늘어나는 목록은 offset을 쓰지 않는다.
항목이 추가되면 offset 기준이 밀려 같은 항목이 두 번 나오거나 건너뛰어진다.

- 정렬 기준과 함께 **고유한 tie-breaker**를 포함한다. 생성 시각만으로 정렬하면
  같은 시각 항목의 순서가 흔들린다.
- 커서는 클라이언트가 해석하지 않는 불투명한 문자열로 준다.
  형식을 언제든 바꿀 수 있게 하려는 것이지 **내용을 숨기려는 것이 아니다.**
  base64는 인코딩이지 암호화가 아니라서 누구나 되돌려 읽을 수 있다.
  따라서 **그 응답으로 이미 나가는 값만 커서에 담는다.** 익명 사용자 ID처럼 응답에 없는 값을
  넣으면 불투명하다는 이유로 감춰졌다고 착각하게 된다.
- 다음 페이지가 없으면 커서를 `null`로 반환한다. **필드를 빼지 않는다.**
  없는 필드와 `null`을 구분하는 클라이언트가 있고, "마지막 페이지"라는 신호는 명시적이어야 한다.
- 페이지 크기는 `size` 쿼리 파라미터로 받는다. **기본 20, 범위 1~50이다.**
  범위 밖은 `INVALID_REQUEST`로 거절한다. 목록마다 다르게 정하지 않는다.
- **읽을 수 없는 커서는 `INVALID_CURSOR`로 거절한다.** 조용히 무시하고 첫 페이지를 주지 않는다.
  클라이언트가 목록 끝에 도달했다고 착각한 채 처음부터 다시 읽어 같은 항목을 반복하게 된다.
  이 코드를 받으면 커서를 버리고 첫 페이지부터 다시 읽는다.
- **값이 비어 있는 커서는 주지 않은 것과 같게 다룬다.** 첫 페이지를 반환한다.
  클라이언트가 `null` 커서를 빈 문자열로 직렬화하는 일이 흔한데, 그때 첫 페이지 요청이
  400이 되면 목록을 시작할 수 없다. 빈 헤더를 없는 것으로 보는 §4와 같은 판단이다.
  커서를 준 적이 없는 요청이므로 바로 위 조항(커서를 줬는데 조용히 무시하는 것)에 걸리지 않는다.
- **형식만 맞고 값이 컬럼 범위를 벗어난 커서도 `INVALID_CURSOR`다.** 쿼리까지 흘려보내면
  DB가 거절해 500이 나가는데, 500은 `retryable`이 `true`라 클라이언트가 같은 커서로
  재시도하게 된다. 커서를 버리라는 신호가 닿지 않아 목록이 그 자리에서 멈춘다.
- 커서에 형식 버전을 넣어 옛 커서가 잘못 해석되지 않게 한다. 형식이 바뀌면 옛 커서는
  `INVALID_CURSOR`가 된다. (`saved/SavedTripCursor`)
- **커서는 위치일 뿐 권한이 아니다.** 남의 커서를 실어도 소유자 조건이 쿼리에 있으므로
  남의 항목은 나오지 않는다.

## 6. 부분 실패 처리

목록에서 일부 항목을 읽지 못하는 경우, **그 항목만 빼고 나머지를 반환**한다.
하나가 깨졌다고 목록 전체를 500으로 실패시키지 않는다.

외부 API 실패도 마찬가지다. 장소 상세는 TourAPI가 죽어도 DB 정보와 결측 표시로 응답한다.

## 7. 로그

- 4xx는 `warn`, 5xx는 `error`로 남긴다. 전역 핸들러가 처리하므로 서비스에서 다시 로깅하지 않는다.
- **요청 본문과 헤더 값을 로그에 넣지 않는다.** 사진 ID 목록, 익명 사용자 식별자,
  임베딩, API 키가 모두 해당한다.
- 추적은 `traceId`로만 한다.
