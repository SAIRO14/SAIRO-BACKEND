# 추천과 코스 생성

사진 선택에서 코스까지 이어지는 계산 과정을 설명한다.

**현재 구현은 MVP 휴리스틱이다.** 정교한 랭킹이나 품질 평가는 없다.
이 문서는 지금 무엇을 하고 있고 그 한계가 무엇인지 남겨, 나중에 바꿀 때 근거가 되도록 한다.

**여기 적힌 것은 현재 동작이다.** 요구사항과 다른 부분은 그 자리에 함께 표시한다.
요구사항 기준은 [requirements.md](./requirements.md)를 본다.

관련 코드: `analysis/TasteAnalysisService`, `course/CourseService`, `photo/PhotoEmbeddingRepository`

## 전체 흐름

```text
선택 사진 (5~10장)
  └─ 임베딩 조회 → 산술 평균 → 대표 임베딩
  └─ 키워드 빈도 → 분위기 태그
       ↓ analysisId로 임시 저장
대표 임베딩
  └─ 코사인 거리로 유사 사진 검색
  └─ 유사 사진의 지역 빈도 집계 → 상위 지역
       ↓
지역별 장소 조회
  └─ 좌표 기반 정렬 → Day 1 / Day 2 분할
```

## 1. 취향 분석

### 대표 임베딩

선택한 사진들의 512차원 임베딩을 **차원별 산술 평균**한 값을 쓴다.

정규화하지 않는다. 검색에 쓰는 pgvector `<=>`가 코사인 거리라 벡터의 크기가 아니라
방향만 비교하기 때문이다.

**한계** — 평균은 서로 다른 분위기의 사진을 함께 고르면 어느 쪽도 아닌 중간값이 된다.
바다 사진과 도심 사진을 반씩 고르면 결과가 흐려진다.

### 분위기 태그

선택 사진의 `keywords`를 쉼표로 나눠 **빈도 상위 5개**를 뽑는다.
화면에는 그중 최대 3개가 표시된다.

원본 형식은 `"밀양 표충사, 재약산, 불교, 종교, 사찰"` 처럼 장소명과 분위기가 섞여 있다.
**현재는 이를 구분하지 않는다.** 그래서 태그에 장소명이 섞여 나올 수 있고,
이는 "선택 단계에서 장소를 숨긴다"는 제품 제약과 부딪힐 여지가 있다.

### 분석 결과 보관

`analysisId`(UUID)를 발급해 대표 임베딩과 태그를 임시 저장한다. 추천 조회 때 이 ID로 꺼낸다.

현재 저장소는 프로세스 메모리 `ConcurrentHashMap`이라 서버를 재시작하면 사라지고,
TTL이 없어 계속 쌓이며, 인스턴스가 여러 개면 동작하지 않는다. → [Q-06](./open-questions.md)

## 2. 지역 추천

### 유사 사진 검색

```sql
SELECT location, keywords FROM photos
WHERE location IS NOT NULL
ORDER BY embedding <=> ?::vector
LIMIT 30
```

대표 임베딩과 코사인 거리가 가까운 순으로 **30개**를 가져온다.
`location`이 없는 사진은 지역 집계에 쓸 수 없으므로 제외한다.

`photos_embedding_idx`(ivfflat)를 타는 근사 검색이라 결과가 항상 정확한 상위 30개는 아니다.

### 지역 집계

유사 사진의 `location` 문자열에서 **첫 공백 이전 단어**를 지역으로 본다.
`"경상북도 안동"` → `"경상북도"`, `"제주도"` → `"제주도"`.

이 단어들의 빈도를 세어 **상위 3개 지역**을 고른다.

**한계** — 문자열을 자르는 방식이라 표기가 흔들리면 다른 지역으로 집계된다.
`"경북"`과 `"경상북도"`가 갈리고, 광역 단위 정규화가 아직 없다.
요구사항의 "광역 단위 문자열 정규화" 항목이 여기에 해당한다.

### 지역별 장소 조회

```sql
SELECT * FROM spots WHERE region_name ILIKE '%' || :region || '%' LIMIT 5
```

지역명 부분 일치로 장소를 최대 5개 가져온다.

**한계** — 부분 일치라 의도하지 않은 지역이 걸릴 수 있다.
장소가 2개 미만인 지역은 코스를 만들 수 없으므로 추천 대상에서 빼야 하는데,
현재는 그 필터가 없다.

## 3. 코스 생성

### 장소 정렬

좌표가 있는 장소만 **greedy nearest-neighbor**로 정렬한다.
**가장 북쪽 장소**에서 시작해 가장 가까운 미방문 장소를 반복해서 잇는다.

거리는 위경도 차이의 제곱합(유클리드)이다. 실제 지구 거리(Haversine)가 아니다.
국내 범위에서 **순서만 정하는 용도**라 단조 관계가 유지되면 충분하고, 제곱근도 생략한다.

좌표가 없는 장소는 정렬하지 않고 `spotId` 순으로 **뒤에 그대로 붙인다.**

같은 장소 집합이면 요청 순서가 달라도 항상 같은 코스가 나온다.
`findAllById()`가 반환 순서를 보장하지 않으므로 시작점(가장 북쪽, 동일 위도면 `spotId`)과
동점 처리(거리가 같으면 `spotId`)를 모두 목록 순서와 무관하게 정했다.

**한계** — greedy는 최적 경로를 보장하지 않는다.
시작점을 가장 북쪽으로 고정한 것도 이동 거리 기준의 최적 선택은 아니다.

### Day 분할

정렬된 목록을 가운데에서 잘라 앞을 Day 1, 뒤를 Day 2로 둔다.
홀수면 Day 2가 하나 더 많다. 요구사항의 "차이 1개 이하"를 만족한다.

**한계** — 좌표 없는 장소가 모두 뒤에 붙으므로 그 수가 많으면 Day 2에 몰린다.

### 지역 검증

통과 조건은 둘이다. 하나라도 어긋나면 `COURSE_REGION_MISMATCH`로 실패한다.

1. 모든 장소의 `region_name`이 **같은 값**일 것
2. 그 값이 요청의 `regionName`을 **포함**할 것 (대소문자 무시)

2번이 부분 일치인 이유는 장소를 고를 때와 규칙을 맞추기 위해서다. 지역별 장소 조회가
`ILIKE '%지역%'`이므로, 완전 일치로 보면 `"제주"`로 조회된 `"제주도"` 장소가 검증에서 막혀
추천에서 코스 생성으로 이어지는 흐름이 끊긴다.

**스냅샷에 저장하는 값은 요청이 아니라 장소의 `region_name`이다.**
`regionName: "제주"`로 요청해도 스냅샷에는 `"제주도"`가 들어간다.
요청 값을 그대로 저장하면 `"주"` 같은 값이 스냅샷에 박힌다. 1번 조건이 그런 요청으로
경주와 제주 장소가 섞이는 것도 함께 막는다.

**한계** — 부분 일치라 조회와 같은 약점을 그대로 가진다. 광역 단위 정규화가 들어오면
조회와 검증을 함께 정리해야 한다.

저장된 지역명은 공유 상세에 표시된다. ([ADR 0010](./decisions/0010-course-persistence.md))

## 4. 현재 상수

한곳에서 바꾸면 결과가 크게 달라지는 값들이다.

| 값 | 현재 | 위치 |
|---|---|---|
| 유사 사진 검색 수 | 30 | `TasteAnalysisService.SIMILAR_PHOTO_LIMIT` |
| 추천 지역 수 | 3 | `TasteAnalysisService.TOP_REGION_COUNT` |
| 지역별 장소 수 | 5 | `TasteAnalysisService.SPOTS_PER_REGION` |
| 분위기 태그 후보 수 | 5 | `parseMoodTags` 내부 |
| 사진 풀 기본 크기 | 40 | `PhotoController` 기본 파라미터 |
| ivfflat lists | 50 | `V1__init_schema.sql` |

지역별 최종 코스 장소 수는 아직 확정되지 않았다. → [Q-05](./open-questions.md)

## 5. 알려진 개선 여지

우선순위 판단용 목록이다. 지금 당장 해야 하는 일은 아니다.

- 광역 단위 지역명 정규화
- 장소가 2개 미만인 지역을 추천에서 제외
- 키워드에서 장소명과 분위기어 분리
- 지역명 부분 일치 조회의 오탐 제거
- 코스 경로 품질 평가
- 같은 사용자에게 반복 노출되는 지역의 다양성 확보
